# Orchestrator — Verification (lazy-loaded)

Parent only: load when Verification fires or a delegated writer returns; not for small work.

## Verification rule (normative)

**Verification rule** (gentle-pi#661/#662): The bounded writer always runs the exact parent-authorized commands under the delegated task's `## Verification` heading, synchronously and in the foreground, and reports each as `<command>: <observed result>` -- see `gentle-ai-worker`'s Verification contract, including how `## Known environmental failures` (exact pre-existing base failures) differs from any other failing required command, which still forces `status: partial`. After the writer returns, when RDD is validated off, do not require `assess`: the writer's self-verification stands and a named Task Size high-risk item still requires an independent verifier. When RDD is on or unknown, call `gentle_review` with `{"operation":"assess"}` over the writer's diff and follow the returned plan. When the line reads `on`, the native review is an additional outside view of the change; it never replaces or skips the tier's verification, and the tier's verifier runs before review. Pass a known `nativeReviewOutcome`; ASSESS derives `closed` only from the native `candidate.consumed` fact for this exact candidate (gentle-pi#1175), so a caller-supplied `closed` is not authority and, without that fact, resolves to `unknown`; the outcome only explains the plan, never lowers it. The tier table:

| Tier | Verification (any RDD state) |
|---|---|
| passive | structural readback by the parent; no separate verifier, no tests |
| medium | writer self-verification stands; no separate verifier, whatever model wrote the change |
| high | only through `escalate` naming a Task Size high-risk item: writer self-verification plus one separate `gentle-ai-verify` run |
| native high, unknown, or assess failed | informs only: writer self-verification stands; escalate when a named high-risk item applies |

Validated off skips native assessment: its fallback is unassessable/medium, never a fabricated passive result. A direct plan request stays read-only, skipping native assess and target status.

The independent verifier runs only when the change touches a named Task Size high-risk item (runtime admits its launch on a `Risk: item N` line or sentence, a feature-document task line, or past the context backstop); never for size, a native tier alone, a failed assessment, or the model or effort that wrote the change. An unknown `Receipt-driven development:` line does not waive named-risk verification. The parent spot check (re-running one reported command before delivery) stays required in every tier. A passive change that reports no command needs only its readback. ASSESS takes the writer profile from the runtime-recorded model and effort of the pending mutations for the root; caller `writerModelId`/`writerEffort` are only a fallback when no runtime evidence exists; the writer profile is reported but never adds a verifier. When native reports them, ASSESS also projects `reviewDue`, `reviewDueReason`, `candidate.consumed`, and the native continuation verbatim; relay it unchanged; never rebuild it. A native code review is not a substitute for applicable functional checks: tests, builds, and functional verification such as browser checks for UI changes still run, and review outcomes never authorize delivery. The change's own focused test and suite run in the session that made the change.

## Agent escalation (gentle-shell#1494)

For Task Size high-risk work when RDD is on or unknown, assess with `"escalate": {"item": <1-6>, "reason": "<one line>"}`. With validated RDD off, name the risk and run the independent verifier without requiring assess; a direct plan request can still pass the same escalation. It adds a verifier only when `escalate` names a Task Size high-risk item; raises to high, keeps `nativeRisk`, returns `agentEscalation`, never lowers a tier. Unsupported: raise this plan, not native review.

## Verifier preparation failure

A failed verifier setup is a preparation failure, not an unavailable verifier capability. A verifier's self-fix of its own setup error (one correction in the same verification) needs no decision; if it made none, relaunch once with the corrected command, unasked. If setup still fails or lacks prerequisites, stop: one **Needs your decision** naming the blocker and exact unrun checks as unverified; never repair helpers more or auto-relaunch for it. If setup fails before probes, preserve the failed attempt and report zero tests run; the checks remain unverified. Setup/infrastructure failures aren't code findings; tooling defects keep the correction bound. After a setup prerequisite is repaired, the human may explicitly request one new bounded verification attempt. This is a new request, not an automatic retry; it does not reset the prior attempt or unrelated budgets. Before proceeding, confirm no child is active or has an uncertain status. Never bypass consent, a denial, explicit one-run or no-retry limits, terminal native outcomes, or exhausted native budgets; on a relaunch, never blindly repeat an oversized copy. Follow **Authorized work continuity** for setup and worker recovery; scratch: `gentle-ai-verify`.

When required proof is unobtainable, one terminal disposition closes a stopped verification: name the missing proof and resume authorized in-scope work at `status: partial` -- never PASS, never silently dropped (gentle-shell#3082).

## Verification proportionality

Before adding or retaining an auxiliary gate, name its acceptance criterion, concrete threat, or authoritative contract; otherwise it must not become a delivery blocker. Do not build a framework for a bounded capability probe; use the existing command path and retain its observed result.

On overengineering warnings, remove or collapse optional artifacts and checks. State what was removed, what remains indispensable, and the next application outcome. Keep required functional checks, security controls, and native review authority intact; do not pass missing proof or weaken permissions.

## Parallel review protocol (gentle-shell#1731)

1. **Self-review**, required by each writer prompt, in its own session before returning: spec sections by reference (#1713), the request's authorized examples, tests, and typecheck; it fixes and continues (one correction per failing check, a second only if the same check still fails, then `partial`), reporting requirement by requirement. Low and medium risk need nothing else.
2. **Independent verify per unit**, once, after its final self-review (never per worker cycle or retry), in parallel when several finish together, only when that unit is high risk: its Risk line, or, when RDD is on or unknown, `assess` over its actual diff or the worker's own `escalate` (high-risk list in Task Size), never inferred from the worker's summary alone. When on or unknown, assess via its work-unit commit (`{"baseRef":"<previous>","committedOnly":true}`) or its own isolated worktree. Parent-written code over several deliveries of one feature: one verify at the feature's end.
3. **Seam check**: after parallel units finish, one full-suite command run by the parent (the parent spot check) catches seams between units.
4. **Verify handoff**: the whole feature document, the assigned unit and its linked `S#` plus affected interactions, the baseline commit, and the probe command forms (tests, CLI, typecheck) for probes on isolated state in a fresh `mktemp -d` scratch copy, never just "read-only"; the runtime removes each subagent's own TMPDIR, which holds that copy; `gentle-ai-verify` holds the checklist. Name the change kind (external tool or environment, prompt or contract text, user-reported failure); for the last, pass verbatim its exact failing command, error text, tool versions and configuration. Run yourself any real-case check the verifier leaves unverified before calling the change verified. Future or unrelated requirements are out of scope, not unmet; final feature verification covers every `S#`. Resolve every in-scope unmet item before closing the unit; the writer adds its probes as regression tests; the parent commits when a commit is authorized.
5. **One correction**: verify blockers get one correction batch that fixes every reported blocker, then one re-verify limited to those blockers, never a new full sweep. Advisories never start a correction. A second correction runs automatically only when the recheck shows the same blocker still failing; a new finding never earns one. Blockers still open after that stop as one **Needs your decision**. A `partial` or `blocked` writer report gets only this correction, never an extra verify run beyond the risk tier's verifier; partial, blocked, unavailable, or exhausted proof left after it becomes that one **Needs your decision**.
