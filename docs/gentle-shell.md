# Gentle Shell reference

Gentle Shell is the `gentle-shell` coding-agent workspace built for Pi, not a theme. The `gentle-pi` package integrates the shell bar, workspace changes, provider usage where Pi exposes it, and native agent orchestration views into a Pi session. Start with the [README](../README.md#features) for the product overview.

For development, use [ODD and feature recovery](readme-reference.md#organic-driven-development). TDD follows configured mode, and native review remains a separate user-owned choice.

Source map: [shell extension](../extensions/gentle-shell.ts), [shell bar](../lib/shell-bar.ts), [changes model](../lib/shell-changes.ts), [changes view](../lib/shell-changes-view.ts), [usage model](../lib/shell-usage.ts), [usage view](../lib/shell-usage-view.ts), [agents extension](../extensions/gentle-agents.ts), and [agent runner](../lib/agents-runner.ts).

Use `/skill:gentle-ui-design` for web and product interface guidance or a read-only critique. Ask it, for example, to improve how people find and compare records or to assess a narrow-screen layout. ## Terminal program identity

`gentle-shell` identifies as `gentle-shell` in native OSC 7501 reports, so terminals and dashboards can distinguish it from plain Pi. The launcher sets `PI_PROGRAM_STATUS_APP=gentle-shell`; the bundled `gentle-program-identity` extension consumes it even when Pi itself does not. Ordinary Pi sessions without that marker, delegated children, RPC, JSON and print modes are unchanged. `PI_PROGRAM_STATUS=1|0` still controls whether the native terminal sends reports.

The extension wraps only the active terminal instance's `setProgramStatus`, preserving Pi's states and messages. Pi can emit an initial `pi` report before extensions load; the extension immediately replays its cached native status with the corrected identity, without waiting for a prompt. The wrapper and guarded startup-cache replay are compatibility adaptations, not an official Pi identity hook; shutdown, reload and session replacement release the wrapper without overwriting later extensions. If a terminal has no compatible cached status, correction begins with its next native report. Disabling this extension removes the fallback on Pi versions that ignore the variable. This changes reported identity, not Herdr's resume-command configuration.

## Updating Pi safely

Run `gentle-shell update` to update the Pi this launcher runs. It also works when that Pi is older than the required minimum version, which every other command refuses. Shell verifies npm/pnpm global listing JSON and canonical package roots before installing exactly one supplying package. This supports pnpm v11 linked stores without relying on `PNPM_HOME` containment. When the launcher runs its adjacent Pi peer, the supplier is the listed `gentle-pi` package itself: Shell is reinstalled at its current version so the package manager re-resolves the peer, because updating a separate global Pi never changes the peer a Shell install runs. A main-channel Shell (`<version>-main.<sha12>`) is never published, so it is reinstalled from the tarball `gentle-shell upgrade --channel main` packed under `<config home>/main/packages/` (an absolute `GENTLE_PI_CONFIG_HOME`, else `~/.pi/gentle-ai`; a relative override is refused); when that tarball is missing, `update` installs nothing and names the rebuild path (`gentle-shell upgrade --channel release`, then `--channel main`), because `upgrade --channel main` alone is a no-op when already at the latest main. A Pi found on `PATH` or through `GENTLE_SHELL_PI` is updated through its own listed global package; a package-manager shim is followed to the single `cli.js` it names. Pi and Shell are never combined into a comma install.

The global installer resolves an exact latest stable Pi after consent when it must install Pi or update an older owned Pi; compatible existing installations are left alone. Its setup-recovery check still accepts only the legacy verified recovery pin, so an interrupted setup after a newer Pi was installed cannot use automatic recovery.

A source-linked Shell uses a separate local route: the exact listed Shell link and selected adjacent Pi must resolve to the checkout. A single-project Git checkout needs an exact `npm@x.y.z` or `pnpm@x.y.z` `packageManager` declaration and a compatible manager on PATH: pnpm may match or exceed the declared version; npm must match its pin. pnpm's `--pm-on-fail=ignore` keeps the checked newer manager instead of downloading the older project pin, without changing the declaration or release-age/security policy. Bundled installations continue to use their own contained manager; source checkouts do not borrow an unverified manager from another prefix. The checkout also needs a direct registry Pi dependency, and exactly one matching lockfile (`package-lock.json` or `pnpm-lock.yaml`). `update` runs a named, range-respecting local update with `--no-save` and lifecycle scripts disabled, preserving the global Shell link and declared ranges. Its Pi/transitive lockfile graph may change. pnpm's metadata cache and minimum-release-age policy still apply: an unchanged version is reported without clearing caches or overriding that policy. The checkout's adjacent Pi is read back after installation; an unreadable version is reported, never invented. Root-only `pnpm-workspace.yaml` configuration is allowed only when the pinned manager's read-only selectors and recursive project listing prove that the checkout is the sole project. Its release-age/security settings are loaded normally, never ignored, and its bytes must remain unchanged. Declared multi-project or ancestor workspaces, conflicting/missing lockfiles, linked manifests/lockfiles and installed Pi source-checkout overrides (including `npm link` without a manifest change) refuse before installation; resolve these layouts manually rather than deleting a lockfile blindly.

Unknown or ambiguous ownership, unsupported source/link packages, and pnpm global groups shared with other top-level packages refuse without installation changes. Separate groups in one aggregated listing are allowed. After the install, Shell reads the supplied Pi version back from a fresh listing and reports whether it changed. pnpm installs only releases older than its `minimumReleaseAge` setting (pnpm 11 defaults to 4320 minutes), so a very recent Pi release is picked up once it is old enough; Shell reports that rule instead of overriding it. Global listings, version probes and global installations run from the system temporary directory so the current project's `packageManager` pin never changes which pnpm answers. Only a verified source update runs from its checkout. Use the supplying package manager for unsupported layouts. `gentle-shell update --extensions-only` remains an extension-only Pi command. Prefix-bundled `gentle-shell update` selects the newest published stable Pi (`--latest` is an alias), without the release's verified lockfile; it warns that features relying on audited Pi internals, such as the Vim editor, may turn off. A later Shell `upgrade` keeps a newer Pi and warns when it must install without the new release's lockfile. Explicit extension pins stay pinned; `--all` also forwards extension updates. Managed Pi self updates reject `--force`. See [managing packages](readme-reference.md#managing-packages) for the ownership contract.

For Pi packages, run `gentle-shell update --extensions`. The bundled Shell-managed `gentle-engram` uses an unversioned package source, so Pi's existing startup notice lists it when a newer version is available; opening Shell does not automatically update it. An older Shell-owned `0.4.2` registration is migrated without an install, while linked/foreign homes, other versions and unrelated pinned packages are left selected. This updates the Pi package, not the native Engram executable.

When the install fails, `update` names the package manager and the exact command it ran, then one sanitized line of that manager's own output. That line is the last error line (`Error:` or an `ERR_` code) in its stdout or stderr, stderr's when both have one, because npm prints its error on stderr while pnpm 11 prints `ERR_PNPM_*` on stdout. A warning on stderr never hides that error. Without any error line, it is the last line of stderr, else of stdout. Terminal escapes and control characters are removed, your home directory becomes `~`, and the line is at most 300 characters. For example:

```text
gentle-shell update: pnpm (/usr/local/bin/pnpm) could not install /Users/you/.pi/gentle-ai/main/packages/gentle-pi-<version>.tgz
[ERR_PNPM_INVALID_VERSION_UNION] Invalid versions union. Found: "gentle-pi@file:...". Use exact versions only.
```

`ERR_PNPM_INVALID_VERSION_UNION` during `update` usually means more than one pnpm is installed: an older pnpm on `PATH` cannot read the `allowBuilds` key a newer pnpm wrote to the global `pnpm-workspace.yaml`. Keep a single standalone pnpm.

## v2.6.0 workspace updates

The [v2.6.0 release](https://github.com/Gentleman-Programming/gentle-pi/releases/tag/v2.6.0) makes the workspace state more durable and inspectable:

- Registered worktrees survive reloads. `/gentle:changes` groups each dirty root (the session's repository and its subagents' worktrees) and shows Git status, line counts, and lazy diffs against HEAD without conflating identical paths from different worktrees.
- Fullscreen pointer navigation and the responsive sidebar keep changes, agents, and TODO usable at changing terminal widths; cached frames avoid redrawing inactive sidebar content while live status still updates.
- The Agents List and Details views preserve the orchestrator/session hierarchy and completion, abort, and lost-exit history. Parent-child queries and notifications have an explicit handoff path, while model, effort, and usage stay observable per task.
- Named `/gentle:profiles` atomically route the orchestrator separately from packaged and review roles, and carry a per-profile orchestrator workflow mode (`w` on the models screen: organic, where the orchestrator may implement inline, or full delegation, where every implementation goes to a subagent); see the [technical reference](readme-reference.md#agent-model-profiles) for the profile model. Full delegation pays off with an expensive orchestrator and light workers; on small tasks it costs a few times the wall time of organic, so see [Orchestrator workflow mode](readme-reference.md#orchestrator-workflow-mode) for the measured cost and which mode to pick.

The source checkout prepares `gentle-pi` `4.0.0` with a package-local Gentle AI `v4.4.0` pin; this does not imply that the package release has been published.

## Shell interactions and runtime behavior

Gentle Shell is the Pi workspace experience provided by the `gentle-pi` package. It follows the Gentle themes: one border language, rose for whatever is alive.

### Modal mouse controls

In fullscreen, visible click targets use the shared orange hover role (`warning` in the active theme). Hover is presentation only: it does not run a command, change a setting, choose an answer, or stop a job. Keyboard navigation remains available.

| Surface | Mouse behavior |
| --- | --- |
| `/gentle:customize` | Click a category, setting row or value. Clicking a value applies it; compact `‹`/`›` arrows follow the same immediate or preview-first behavior as the keyboard arrows. Confirmations still require an explicit click on `y yes` (or the `y` key); click `cancel` to decline when visible. |
| `/gentle:commands` | Click a visible command to run it; use the wheel to navigate the filtered list. Headers and clipped rows are not targets, and mouse activation is disabled during shortcut capture. |
| `/gentle:jobs` | Click a visible job to select it, and use the visible list/details, Stop and close controls. Stop applies only to a currently running job; hovering never changes the selected job or stops it. |
| Questionnaires and response selectors | Existing option clicks keep their single-select, multi-select and custom-answer behavior; selectable labels now use the same hover role. Questionnaire tabs remain keyboard-controlled. |

Moving to blank space inside a modal, keyboard navigation, resizing and disposal clear its hover. Native centered-overlay routing does not deliver motion outside the card, so the previous highlight can remain until the pointer returns or the view changes. Hover also depends on the terminal forwarding motion events; clicks remain usable when a multiplexer does not forward plain motion.

In regular mode the terminal owns mouse input, so use the keyboard instead. Review-consent dialogs are not changed by these modal controls.

### Fullscreen layout

Open `/gentle:customize` → **Layout** to adjust placements, spacing and task-summary publishing:

- **Task summary:** `on` (the default) or `off` controls the active-task summary published to terminal tools, such as Herdr's sidebar. Highlighting a choice does not save it; Enter or Space saves and applies it now. The `enabled` preference lives in `herdr-task-summary.json` in the Gentle Pi config home, separate from visual profiles. Existing colors are preserved; malformed or unreadable files are not overwritten. This does not edit Herdr config or hide the local Todo list.

- **Density:** `comfortable` adds spacing around the bars and between rail sections. `compact` removes those gaps except between transparent float cards; `minimal` also removes gauges and usage shortcut hints from the fullscreen bars while retaining their values when space permits.

At 140 columns or wider the placements share the split status bar's design. Comfortable centers the bar between two margin rows on the chrome surface; compact and minimal draw the bar row alone. A registered extension shortcut always wins over these selection keys.
- Pi's paste-image key (`app.clipboard.pasteImage`: `ctrl+v`, or `alt+v` on Windows) turns a clipboard image into an `[Image#N]` chip instead of a temp-file path. One Backspace or Delete removes the whole chip; cursor and word motions, word deletion, wrapping and Vim NORMAL treat it as one unit. On submit, every chip still in the draft is sent as a real image attachment, so the model sees it without calling `read`. A deleted chip is never sent. The bytes stay in memory; no temp file is written. See [Pasted images](#pasted-images).
- If another extension already installed a custom editor, Gentle Shell leaves it alone.

### Pasted images

While a draft holds chips, a strip above the prompt lists each one:

```text
[Image#1] png · 1280×720 · 84 KB
```

- **Preview:** terminals with an image protocol (Kitty, Ghostty, WezTerm, Warp, iTerm2) draw a small thumbnail under each label while the agent is idle. While it works, and in terminals or multiplexers that hide the protocol (such as tmux), the label alone is shown, so streaming never re-sends the image to the terminal.
- **Clipboard sources:** the native clipboard on macOS and Windows; `wl-paste` or `xclip` on Linux. On WSL, a Windows screenshot (`Win+Shift+S`) is read from the Windows clipboard through `powershell.exe`, because the Linux clipboard never receives it.
- **Pasted paths:** an image that arrives as a file path also becomes a chip. Herdr's desktop app and `herdr --remote` hand a clipboard image to a terminal on another machine as a temp file and paste its path (`herdr-paste-*.png`, `client-N-clipboard-*.png`); dropping images on a Herdr pane, or copying image files in a file manager, pastes quoted paths. Up to eight paths are read from the file itself, with spaces, `~` and `file://` forms. A paste that is not made only of image paths still goes through Pi unchanged.
- **What stays Pi's:** text, other files copied in a file manager, and image formats other than PNG, JPEG, WebP and GIF go through Pi's own paste handler unchanged.
- **Models without image input:** the strip warns before you send. If you send anyway, each chip becomes `[Image#N omitted: the current model does not accept images]` and a notice explains why, so nothing is dropped silently.
- **Numbering:** numbers keep counting up for the whole session, so a chip recalled from prompt history never points at a newer image. A recalled chip is plain text; paste the image again to attach it.
- **Sending while the clipboard is read:** reading the Windows clipboard on WSL takes about a second. If you send the message before it finishes, the image is discarded with a notice instead of landing in the next draft; paste again to attach it.
- **Vim NORMAL:** the paste key enters INSERT and pastes the chip. NORMAL motions step over a chip as one unit; an operator whose range covers a chip removes it whole.
- **Terminals that capture the paste key:** some terminals keep `ctrl+v` for their own paste, and nothing reaches Pi when the clipboard holds only an image (Warp on Windows does this). Bind a second key in `~/.pi/agent/keybindings.json`, then restart:

  ```json
  { "app.clipboard.pasteImage": ["ctrl+v", "alt+v"] }
  ```

### Changes

Changes shows the **current Git state** — working tree against HEAD, untracked files included — of the session's repository and of every worktree or repository its subagents used that still exists. Nothing is scanned at startup; the list fills at the first turn end or when the panel opens, then refreshes at each turn end and while the panel is open. Fullscreen, the sidebar, and mouse interaction are unchanged.

```text
✎ 3 files · +42 −7 · extensions/gentle-shell.ts, lib/shell-bar.ts, tests/x.test.ts · /gentle:changes
```

### What appears in Changes

- One group per root: the session cwd's repository, worktrees registered with `session_worktree_register` or launched for subagents, and independent repositories of authorized foreign subagents. Captured write/edit evidence only tells Changes which roots exist; Git supplies the file inventory, with the dependency-backup exception below.
- Committed work disappears because Git no longer reports it; a removed worktree disappears because its directory is gone; a root whose Git fails or times out is omitted while the others stay.
- Each group header shows that root's branch, `no commits yet` for an unborn branch, or `detached` for a real detached HEAD.
- Edits from your editor, shell commands, or other tools appear too: Changes reflects Git, not attribution.
- Untracked files inside `node_modules.backup-*` directories are automatically excluded before counting lines, at any depth; no `.gitignore` setup is needed. The suffix must be nonempty. Tracked files in those directories and ordinary new source files remain visible. Other unwanted artifacts can still be excluded with `.gitignore`.

### Bounds and session lifetime

Changes lists every changed file outside the untracked dependency-backup exclusion without a count limit. One selected diff is bounded at 1 MiB or 20,000 lines; beyond that the panel shows "Diff too large — press o to open in editor." If Git times out, partial diff output is discarded and the pane shows "no diff for this file"; press `o` to inspect the file in the editor.

Captured evidence (`gentle-pi.session-change/v1`) is still stored for session statistics and root discovery, capped at 256 operations and 4 MiB per session, without affecting the Changes list. Reload and resume read the same state from Git; new sessions and forks do not inherit another session's worktrees.

### Browse changes

`/gentle:changes` or `alt+g` opens the two-pane viewer full screen, like Gentle Agents. Worktrees are accordion groups on the left; each file row leads with its status marker (`M` modified, `A` new and staged, `U` new and untracked, `D` deleted, `R` renamed), then its name, its line counts and its directory. Selecting a file shows its full path on the first row of the right pane (clipped from the left so the name stays visible) and its diff against HEAD below it; untracked files show their full content.

- `j`/`k` or arrows navigate. On a group, Enter, Space or Right expands it; Left returns to its parent or collapses it. `ctrl+j/k` or Page Up/Down scroll the diff; Escape or `q` closes.
- `F` toggles diff-only mode at any width: the file list and its separator hide so the diff uses the full width. There `j`/`k` still move between files (across worktrees; the path row shows which), the scroll keys and the wheel scroll the diff, `o`/Enter and `r` keep working, the first Escape returns to the file list, and `q` closes. Every opening starts with the file list visible.
- Fullscreen left-click selects files; mouse wheels scroll the file list and diff independently. Hovering an unselected row (worktree or file, in either pane's list) paints it in the same shared hover role every clickable surface in the shell uses; it never opens or selects the file, and never overrides the already-selected row's own role.
- Opening, pressing `r`, and the overlay's refresh cadence re-read each root's Git status; a same-line-count edit reloads the open diff.
- On a file, `o` or Enter opens the actual current file in `$VISUAL` or `$EDITOR`, with its worktree as cwd. Editor launches pass paths as literal arguments, never through a shell. On Windows, configure a direct executable (for example `notepad.exe`); `.cmd`/`.bat` editor shims are refused. Launch failures appear as warnings after the terminal UI is restored. This also applies when opening an Agents session transcript. Editor commands retain literal-space splitting: quoted executable paths and shell expressions are not supported.
- `GENTLE_PI_SHELL_CHANGES_KEY` rebinds the shortcut; `off` disables it. `GENTLE_PI_SHELL_CHANGES_POLL_MS` controls how often the open overlay re-reads Git. `GENTLE_PI_SHELL_CHANGES_WATCH_MS` no longer enables filesystem polling.
- No uncommitted changes in the session's roots means no widget and an informational notice.

### Command palette

`/gentle:commands` or `alt+k` opens a curated, grouped command menu, OpenCode-style — not a raw listing of every registered extension command. Entries are grouped under Configuration, Session, Diagnostics, and Skills, each shown by a human label with its current key where it has one (a key saved but not yet applied reads `(reload)`); a command only appears when it is both in the curated set and actually registered. ### Guided tour

`/gentle:guide` gives a guided tour of Gentle Shell, one step at a time, in the style of [driver.js](https://driverjs.com/). ### Keymaps

Every Gentle shortcut, and any command in the palette, can get a key of your choice:

- In the command palette, `tab` assigns a key to the highlighted command.

| Rule | Behavior |
|---|---|
| Typing keys | Only keys with `ctrl` or `alt` (with or without `shift`), or `f1`-`f12`, can be assigned. |

- For Codex, usage comes from the same account usage endpoint the Codex CLI reads, using the OAuth token pi already holds. It is fetched at session start, at most every 5 minutes after a turn, and on `r` in the panel. Rate-limit headers on SSE responses are picked up too. Codex windows require a finite positive duration reported by the provider; missing or invalid durations are ignored, never shown as `0m` or replaced with an assumed `5h` quota. A real `0%` remains visible when its window is valid, and a response with no valid header windows leaves the previous snapshot untouched. The same refresh covers every provider the session targets: the active model's own provider plus every provider the session profile's subagent routing names — the same profile subagent launches use: the profile selected in this session, otherwise the profile the session froze at startup from the local pin, the repository declaration, or the global active profile (see [Session profile frozen at startup](readme-reference.md#session-profile-frozen-at-startup)). Each provider keeps its own 5-minute window, its own stale-source guard, and its own last good snapshot. Providers refresh concurrently, each inside its own bounded window (default 10s, `GENTLE_PI_SHELL_USAGE_TIMEOUT_MS`): the abort signal reaches the underlying fetch — composed with the caller's own signal when it carries one, never replacing it — a provider that outlives its window wears the generic failure note, and whatever it answers afterwards is discarded — a late answer never replaces what the timeout settled, exactly like the stale-source guard above.
- A routing entry names its provider with a qualified ref (`provider/model`); a bare model id is resolved through the model registry only when exactly one provider carries that id, and is left untargeted rather than guessed when none or several do. The targeted scope is resolved when a refresh runs — at session start, on each turn's throttled refresh, on `r` or reopening the panel, and when a usage source registers — so a profile selected in the session (or a default change in `follow` mode) is picked up by the next refresh rather than live per render.
- For Claude Pro/Max, usage arrives in the rate-limit headers of every response, so the 5h and weekly windows appear after the first turn. `pi-claude-bridge` 0.9.3 and later forward Claude Code's usage updates as those same headers, so a `claude-bridge` session shows them too. A header snapshot is filed under the provider that served the response (the session's `claude-bridge`, not `anthropic`), and falls back to the provider the headers name only when no model is known.
- For NaN Cloud, usage comes from the quota endpoint the official dashboard reads, with the same API key pi already holds. Each metered model reports one allowance for the billing period, and that window carries no label: the model id names it in the bar and the reset text says what it is in the panel. A model that also reports a rolling window shows that one labeled next to it (`4h`), which today's payload does not send; percentages are tokens used over the allowance, exactly as the dashboard draws them, and the allowance is the full-period cap (`fullCap`) whenever the model reports a positive one, because `cap` alone is the prorated allowance of the period in progress. It is fetched under the same 5-minute rule as Codex, counted per provider so a switch fetches the provider it switched to, refuses redirects so the bearer cannot be replayed to another origin, and keeps no cached copy. The endpoint sits outside NaN's published OpenAPI, so the parser reads it defensively: a model that reports no allowance is skipped, as the dashboard skips it, while a metered model whose usage cannot be read fails the whole read, so a partial payload never replaces a complete snapshot with a cheaper-looking one. A session that already has a snapshot keeps the last valid one through a malformed payload or a failed fetch, and the pending note appears only while there is nothing to draw. NaN now bills from a shared credit pool, but its credit balance is not readable with an API key, so these rows are NaN's per-model token quota, not the balance: the panel says so under the NaN rows (`per-model token quota · not your credit balance`), rows for models outside the maintained NaN catalog (such as the retired `glm5.2`) are dropped, and the quota never puts a NaN model or the NaN provider on cooldown.
- Extensions can register a usage source for their own provider: gentle-shell has no built-in knowledge of it, but treats it exactly like Codex or NaN once registered. Emit `gentle-pi:usage-source/v1` on `pi.events` with `{ schema: "gentle-pi.usage-source/v1", provider, pendingNote?, fetch(apiKey, fetchFn, now) }`, where `fetch` resolves a `ProviderUsage` the same shape the built-in providers produce, or `undefined` when there is nothing to show yet. A malformed payload, a `fetch` that isn't a function, a provider id outside the safe id pattern, or a `fetch` call that throws or rejects is ignored rather than crashing the shell. The `fetchFn` a source receives is bounded the same way: once the provider's window expires it aborts, and a later resolution is discarded. Re-registering the same provider replaces its source, so emitting again at every `session_start` is safe and keeps load order irrelevant. Once registered, the provider shows `pendingNote` (or the same "no usage yet · r to fetch" default the built-ins use) until its first fetch, and a registration that arrives after the session already started, for any targeted provider (the session's own or a subagent route of the session profile), triggers one immediate refresh of that provider instead of waiting for the next turn or the 5-minute window. Example, using a neutral provider id:

  ```ts
  pi.events.emit("gentle-pi:usage-source/v1", {
    schema: "gentle-pi.usage-source/v1",
    provider: "acme-cloud",
    fetch: async (apiKey, fetchFn, now) => {
      if (!apiKey) return undefined;
      const response = await fetchFn("https://acme.example/usage", { headers: { Authorization: `Bearer ${apiKey}` } });
      if (!response.ok) return undefined;
      return { provider: "acme-cloud", plan: "Acme · 42 credits", limits: [], fetchedAt: now };
    },
  });
  ```
- The bar names the subscription it shows (`codex`, `claude`, a NaN model) and always follows the active model. A provider with per-model allowances draws the session model's own meter, falling back to its family and then to the account total (NaN stops at the family: an account total of NaN quotas would read as a balance it is not), never to whichever model the payload happens to list first — and that holds for a payload that reports a single metered model too, because one allowance is still per-model data rather than a reason to echo the first entry. The panel puts the active provider first, marked with the petal, and says why it has no data when it does not: API-key providers have no subscription windows, Claude reports after the first response, Codex and NaN wait for a fetch. It draws exactly the targeted providers, in scope order — a targeted provider with no snapshot explains itself, and one whose latest refresh settled without a snapshot wears a generic nonsecret "fetch failed · r to retry" note: beside its retained snapshot when it has one, or in place of the pending note when it has none. The note tracks actual failures only — a refresh still in flight never reads as failed, Claude (headers-only) is never dressed up as one, and the next successful refresh clears it. A provider recorded under a previous profile's routing is not current scope after a profile switch. A provider without per-model allowances keeps its single aggregate line in the sidebar, unchanged.

### Gentle Agents

The current package requires Pi 1.2.0 or newer and Node `^22.19.0 || >=23.6.0` (22.19.0 or a later 22.x release, or 23.6.0 or newer; Node 23.0–23.5 are not supported). Development tests resolve Pi through the open `>=1.0.0` development range. Use the latest Pi release; gentle-pi does not update your installed Pi automatically. Children, including any `GENTLE_PI_AGENTS_PI` override, must emit `agent_settled`: `agent_end` records a run's output but is not completion because retries or queued continuations may follow.

The `subagent_*` tools and the agents card replace the third-party subagents package (remove `npm:pi-subagents-j0k3r` from your pi packages; while it is still installed the tools stay unregistered and a warning says so at startup). Agent definitions and settings are the ones you already have: markdown agents in `~/.pi/agent/agents/`, `~/.pi/agent/subagents/`, `<cwd>/.pi/agents/`, `<cwd>/.pi/subagents/` (project beats global, `subagents/` beats `agents/`), and `subagents.json` at the global and project level (`default_model`, `default_effort`, `default_mode`, `model_profiles`, `stall_timeout_ms`, `tool_stall_timeout_ms`, `max_concurrency`, `history_max_tasks`, `report_max_bytes`). A finished child's report is delivered into your context up to `report_max_bytes` (default 16384) UTF-8 bytes; a longer one arrives as its head, a truncation line with the exact byte counts naming `subagent_result`, and the end of the report (its last 2048 bytes at most, from a line start), so a closing summary that a memory provider reads from the delivered text is not lost (a report whose part after the head is 2048 bytes or less is delivered whole); a report from a `jd-*` or `review-*` agent, or one that is a single JSON object or array, is never cut, and `subagent_result` returns the full text.

Agent paths follow `GENTLE_PI_AGENT_HOME`, then `PI_CODING_AGENT_DIR`, then `~/.pi/agent` for definitions, config, history, child sessions, and transcripts. These overrides select the agent profile; they do not sandbox project or shared global resources.

The card is above the editor in every mode, including fullscreen — it is not one of the sidebar's cards. Each metadata field (`model · effort`, tokens, cost, elapsed) gets its own fixed, right-aligned column sized to the widest value among the shown tasks, so the numbers line up vertically even when one row's values are much shorter than another's; a queued task fills only the elapsed column with the word `queued`, leaving the rest of the row blank rather than overwriting it. When the card is too narrow for every column, it degrades one column at a time and the same way for every row: the task text goes first, then the `model · effort` label, then tokens, then cost; elapsed is the last column standing, since it is the one value the reader cannot rebuild from anything else on screen.

Every subagent is its own `pi --mode rpc` child process, so the terminal never runs subagent work: the host reads JSON lines, applies each one as a small delta to a bounded per-task thread, and notifies only the listeners of that task. A task-mode child's question (`ctx.ui.select`, `confirm`, `input`, `editor`) reaches you as an ordinary pi dialog; a background child's question is dismissed. Subagents have no automatic total execution timeout: a long-running child remains live while it continues emitting RPC events. A silent child still times out through the configurable `stall_timeout_ms` watchdog (default four minutes). An announced tool call that is still running is live work, not silence, so it is bounded by `tool_stall_timeout_ms` instead (default 30 minutes, never below `stall_timeout_ms`). Closing pi stops the children that are still running.

Delegated children (`GENTLE_PI_AGENTS_CHILD=1`) load the same context files as their parent, minus the gentle-ai managed blocks that bind themselves to the orchestrator, such as `orchestrator` and `agent-routing` (the full list lives in [`lib/child-context-files.ts`](../lib/child-context-files.ts)), and minus the `engram-protocol` memory block, which gentle-engram injects itself every turn. Every other managed block (for example `codegraph-guidance`, or `remote-authorization` nested inside `agent-routing`) and all unmanaged project text reach the child unchanged. A marker counts only when it is alone on its line outside fenced code; if a file's markers are unbalanced, mismatched, or ambiguous, that file is passed through unfiltered. The filtering lives in the packaged `extensions/child-context.ts`, which every child loads (see below); if that file is missing, the child starts without it and keeps today's unfiltered context. The extension registers only a `before_agent_start` hook and does nothing outside a child session; the primary session applies the same filter itself while Gentle Shell injects its own orchestrator prompt. Only the injected context is filtered: every file on disk keeps all of its blocks, so a runtime that reads the same file as a workspace file and carries no runtime-injected protocol (OpenClaw) still gets the `engram-protocol` block.

Children of the package-owned `gentle-ai-worker`, `gentle-ai-explore`, and `gentle-ai-verify` agents start without Pi's skills catalog: the parent passes the exact skill paths they need, which they open with `read`. Gentle Agents sets `GENTLE_PI_AGENTS_NO_SKILLS_CATALOG=1` for those children, and `extensions/child-context.ts` empties the loaded skills before the first prompt, so no `<available_skills>` section is sent under either launch form, including the package's own skills in the Gentle Shell launch below. An agent with one of those names in a project `.pi/agents/` or a `subagents/` directory, and every other agent, keeps the full catalog.

In the isolated Gentle Shell home, `settings.json` does not declare gentle-pi; the launcher injects it with `-e`. So that children load the same package as the parent, the launcher also exports `GENTLE_SHELL_CHILD_PACKAGE_INJECTION` with that exact `-e` set, and Gentle Agents forwards the same set to every child as `--extension` arguments, plus `--no-extensions` when the launch replaced the configured extensions (a takeover). A child then has the same package commands, tools, guardrails, skills, and prompts as a regular gentle-pi child, where `settings.json` declares the package:

- Children skip parent-only startup work: package asset install, model configuration, the skill registry, and history capture.
- A guardrails command classed `confirm` becomes a child question like any other above: a task-mode child asks the parent user and waits for the answer; a background child's question is dismissed.
- A tool the agent requests in `--tools` that does not exist in the child when its first prompt starts adds a task note, for example `gentle-agents: requested tools missing in child: codegraph`. MCP tools (`mcp__*`) are not checked because they register later.
- Without the signal, for example after a manual `pi -e <package>` launch, children fall back to `extensions/child-context.ts`, `extensions/child-safety.ts`, and `extensions/nan-provider.ts` only, with no missing-tool note. That fallback list is frozen; new child behavior ships in the package.
- A takeover forwards every package the parent loaded, so a settings package with no extensions (for example a skills-only package with only a `package.json`), which already makes the takeover parent fail with `Failed to load extension`, makes the child fail the same way; this limitation predates forwarding.

Sending selects the sole advertised peer or asks the user to choose; outbound messages require explicit interactive human consent before dispatch (Allow once, Allow for this session, or Deny), and fail closed if interactive UI or its selector is unavailable, even after a session grant. Each send requires a caller-supplied reason with at least 8 characters after trimming and at most 512 UTF-8 bytes. The consent preview visibly escapes controls and Unicode line separators; the delivered message remains unchanged. A successful ACK means the peer accepted the notification for delivery, not that it read or completed work. This is notification-and-ACK transport only: it has no cross-session queries, offline queue, retries, broadcasts, or read/completion guarantees. On Unix, presence records remain in the profile's private transport directory while socket endpoints use a private, profile-hashed directory below the canonical system temporary directory, keeping endpoint length independent of the profile path and at most 100 encoded bytes. The shared system temporary parent is only validated (current-user-owned without group/other write, or root/current-user-owned, world-writable, and sticky); it is never claimed, permissioned, or cleaned up by gentle-pi. On POSIX, the transport uses private Unix-domain sockets; on Windows, it uses private named pipes scoped by the current account SID, served by a package-local PowerShell helper (`runtime/windows-session-transport.ps1`): the transport selects that fixed helper, and availability and delivery depend on the helper's bounded startup and pipe checks. Notification and ACK limits remain bounded across platforms.

  Windows discovery checks pipe availability without connecting or consuming an accept slot. Each check waits at most 1ms, over at most 64 directory entries; only a missing pipe is classified as dead. Busy pipes, timeouts, access errors, and other inconclusive results retain unknown reachability. Dead records are omitted even if cleanup cannot safely acquire them. Best-effort cleanup revalidates the exact file identity, private ACL, and record contents through a rooted handle that prevents write/delete sharing, checks pipe absence again, and deletes through that same handle. Reopening a session creates a separate activation; cleanup does not remove its newer record.

Validation happens before queueing; the child runs at that canonical root. Successful OS spawn registers it in the originating parent's same-clone registry, including delayed queued launches; failed spawns do not register.

A direct interactive parent must grant that clone before queue or child session-directory writes. Its **↩ Agent answer** card uses the success color when the task completed and the error color otherwise. A completion whose forwarding fails stays queued for the next turn boundary instead of being lost. An idle parent has no boundary coming, so a failed delivery or a wake the host rejects there is retried after the wake grace, at most three times in a row.
- A configured child can call `subagent_parent_message` with bounded, well-formed Unicode text. Notifications retain their existing admission semantics. On timeout the child is told the parent did not answer in time, that a late answer may still arrive as a message, and to continue with what does not depend on it and state the open question in its report. The current parent session alone can reply, once per request. The first admitted task-mode query ends the original tool response while its child keeps running; its eventual non-cancelled completion returns once as a follow-up only if that same session is still active. Channel closure prevents later sends and automatic retry is not provided. Peer transport, offline delivery, retries, and broadcasts are unsupported.

### Background jobs

Use synchronous bash for local, finite, deterministic checks reasonably expected to finish within 30 seconds, with an explicit timeout <= 30 seconds (30 included). Use `bash_background` for longer or unknown duration, external waits, CI, builds, and servers. Inline means the same parent, not necessarily synchronous bash. Report a timeout as failure; never automatically retry, restart, or migrate it to background. Preserve RED/GREEN and public-check exit codes, stdout, and stderr; do not defer or batch Engram bugfix saves and session summaries or bypass RDD. This is agent-facing guidance, not runtime enforcement and not a performance guarantee.

Waiting on CI, a build, or a server should cost neither a `sleep` loop nor a subagent, and neither should reacting to a log or a CI run while it progresses. `bash_background` runs a shell command in the background and returns a job id at once; the agent ends its turn or keeps working, and when the command exits the agent gets one message with the exit code, the last output lines, and the output file path. The wait condition lives inside the command, so its exit is the event:

```bash
gh run watch 12345 --exit-status                           # CI finished
until curl -sf localhost:3000/health; do sleep 1; done     # server is up
```

- Jobs run through Pi's own Bash execution: your configured `shellPath` and `shellCommandPrefix`, a process group per job, and process-tree kill. `bash_background` is a separate tool; native `bash` is unchanged.
- The exit notice uses the same delivery as background subagent results: it is steered into a running turn at the next turn boundary, or stored and wakes an idle session. A job the agent stops with `job_stop` sends no notice; one you stop from `/gentle:jobs` is reported to the agent as stopped by the user.
- stdout and stderr go to a temp file (`gentle-jobs-*/job-N.log`), never into the context; the agent reads it with `read` when it needs more than the tail. The tail keeps the last 20 lines, each capped at its newest 2,000 characters, and the log directory is removed when the session shuts down.
- `bash_background` passes through the same command confirmation, YOLO waiver, and child safety guards as `bash`.
- While the orchestrator has background work running (a subagent task or a background job), a `bash` call that only sleeps (`sleep 10`, `sleep 2m`, or several such sleeps joined by `&&`/`;`) is refused with a message to end the turn, because each completion already arrives as its own message. Wait conditions such as `until ...; do sleep 1; done`, sleeps mixed with real commands, `bash_background`, and `monitor` are never refused, and `sleep` is unrestricted when nothing runs in the background.
- Jobs live in memory, belong to the session that started them, and are stopped when the session shuts down. At most 25 run at once.
- `monitor` is a background job whose every output line is an event, delivered while the command keeps running — for example `tail -f app.log | grep --line-buffered ERROR`, or a loop that prints each CI check as it finishes. Lines within 200 ms share one notice of at most 20 lines (the rest are counted, and stay in the log); notices waiting for a busy agent coalesce. `timeout_seconds` is mandatory (1–1800): the monitor is stopped when it expires and reports its event count. One that prints more than 120 lines within 60 seconds is stopped as a flood, so filter its output. When the command exits, a final notice reports the exit code and event count. It goes through the same command guards as `bash`.
- `/gentle:jobs` opens a full-terminal overlay with this session's jobs beside the selected job's command, status, output file, and live output tail; `↑`/`↓` or `j`/`k` move, `s` stops the selected running job, `q` closes (narrow terminals: `Tab` toggles details, `Escape` goes back). In fullscreen, click a visible job or the details, Stop and close controls; hovered targets use the shared orange role, and Stop rechecks the selected job's current identity and running status. The footer shows `⧗ N jobs` while any run. In fullscreen at 140 columns or wider, running jobs also get their own collapsible sidebar card (`⧗ Jobs`), one row per job with its elapsed time, newest first; it paints nothing only while nothing is current — no running jobs and no finished result still inside its 60-second tail, the Status card never repeats it, and `ctrl+shift+j` (or clicking the card's header) collapses it; `GENTLE_PI_JOBS_KEY` remaps the shortcut, with an empty value or `off` disabling it.

### Conflict markers in commits

The session refuses a `git commit` run through `bash` or `bash_background` when it would record leftover merge conflict markers, and names each `path:line`: at most five, then `and N more`. The command is not run, and the agent is told to resolve the markers and retry, and how a file that holds markers on purpose is exempted.

- It checks the lines that would be added. A plain commit or a `merge`, `rebase`, `cherry-pick`, `revert` or `am --continue` checks the staged content, `commit -a` checks tracked worktree changes, and `commit <paths>` checks those paths. A `git add` or `git stage` earlier in the same command (across `&&`, `;` and new lines, with the same `cd` or `-C` directory) is checked too, because the hook runs before it: named paths and `.` add their worktree content, untracked files included; `-A`/`--all` adds every tracked change and every untracked file that is not ignored; `-u` adds tracked changes only. File names are read as NUL-separated Git output, so spaces, quotes and non-ASCII names are exact.
- When a commit concludes a merge, or a picked commit during `cherry-pick` or `rebase`, a marker line counts only when it is added against both `HEAD` and the other side (`MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REBASE_HEAD`): unresolved markers are in neither, and a file that arrived whole from the other branch is not this commit's addition. `revert` and `am` have no such side and are checked against `HEAD` only.
- A marker is a line starting with `<<<<<<< `, a line that is exactly `=======`, or a line starting with `>>>>>>> `. A file counts only when its added lines include both an opening and a closing marker, so a lone `=======` Markdown underline passes, and binary files are skipped.
- For a file that contains markers on purpose, such as a fixture or a document that shows a conflict, set Git's own `conflict-marker-size` attribute in `.gitattributes`, for example `docs/conflict-example.md conflict-marker-size=32`. Markers that a file already contained before this commit do not count.
- `git -C <dir>`, a leading `cd <dir> &&`, `builtin cd` and `command cd` select the repository that is checked. Redirections (`2>&1`, `>&2`, `&>file`, `> /dev/null`, `< file`) belong to their command and keep that directory, and a backslash at the end of a line continues the command, so flags and paths on the next line count.
- Not checked, and let through without a message: pushes (the range a push publishes depends on remote refs that may be stale or missing offline, so a check would block legitimate pushes of content already published; every commit made in the session is checked instead); wrapped shells (`sh -c`, `eval`, `env`, a `cd` with options); `GIT_*` variables, `--git-dir` and `--work-tree`; `git add -p`, `-i`, `-e`, `-N`, pathspec magic (`:(...)`) and shell globs, whose staging cannot be predicted (the existing index is still checked); a direct `git merge <branch>` that completes without stopping; untracked files over 1 MiB, binary files, and more than 200 candidate files per check; a diff over 16 MiB; and anything Git cannot answer within the 5-second budget for the whole check, or outside a repository.
- This is a mechanical guard, not a review. It runs whether RDD is on, off or unknown, and only after the RDD pre-delivery check, whose denials take precedence and are unchanged. It does not run in subagent sessions and never writes to the repository.

### Gentle Todo

The `todo` tool and its card replace the third-party todo extension (remove `npm:@juicesharp/rpiv-todo` from your pi packages; sessions written by it replay into the new card).

```text
╭─ ❀ Todos · 1 of 3 ──────────────────────────────────────╮
│ ✓ Add quiet tool rendering                              │
│ ◐ Fix quiet tools conflict · fixing conflict            │
│ ○ Show git bash tails                                   │
╰─────────────────────────────────────────────────────────╯
```

The runtime helps keep the list current beyond a static tool description:

- `write` replaces the whole list in one call, so the model rewrites the plan instead of patching it; `add`, `update`, `clear`, and `list` remain for single moves.
- Each agent run's system prompt carries the same byte-stable rules block (in_progress before starting, done right after finishing, update before ending the run), so the cached prompt prefix never changes because of the list. While tasks stay open, the current list reaches the model as a hidden conversation message appended whenever the list changes, and closing the list appends a hidden "no open tasks" marker; the list never enters the system prompt and requests stay append-only, so status, title, note and ordering changes cost only the tail of the conversation and keep the provider prompt cache (Anthropic breakpoints, openai-codex input deltas) warm. When the conversation no longer holds the current list (after compaction, branch navigation, or in a session recorded before this behavior), the next request carries it once and it is saved at that same place, so later requests still extend it.
- A list that goes two agent runs untouched while pending or in-progress tasks remain turns amber with `stale · N turns` on the card; that age is shown to the human only.
- Within a long run, after four tool-use model turns without a successful todo write, the next model request receives one hidden reminder to review the plan; it is saved where that request carried it, so the following requests extend it and the prompt cache keeps its prefix. A successful `write`, `add`, `update`, or `clear` resets and rearms it; `list` and rejected writes do not. The turn containing the write does not count toward the threshold. Empty, finished and blocked-only plans receive no reminder. Reminder tracking restarts when the session loads; it does not change the existing card freshness, show a message in the conversation, start an extra model turn, change task statuses, or connect to subagents.

Tasks are `pending` (`○`), `in_progress` (`◐`), `blocked` (`⊘`), `done` (`✓`), or `dropped` (`✕`):

- `blocked` is open work that waits on something outside the list, such as an admin, another team, or an authorization. It requires a note naming what it waits for, shown next to the title (`⊘ Deploy the cleanup job · waiting for an admin`). Blocked tasks keep the list open, but they never make it stale, and the collapsed card skips them for the next task.
- `dropped` marks a task a change of plan made obsolete. It renders dim without strikethrough, leaves the `done of total` count, and does not count as open, so a list whose remaining tasks are all `done` or `dropped` is finished. `cancelled`, `canceled`, and `abandoned` are accepted as aliases.

A finished list stays on screen for the turn it finished in and clears at the next. `ctrl+shift+t` collapses the card to one task line, truncating long titles and notes with `…` (`GENTLE_PI_TODO_KEY` rebinds it, `off` disables it); `GENTLE_PI_TODO=0` disables the tool and the card.

Expanded cards reserve at most one third of the terminal height (up to 16 rows, with a minimum for card chrome), both in the sidebar and above the editor on narrow/mobile terminals. Scroll the full task text with the wheel in fullscreen mode or `alt+shift+up` / `alt+shift+down` in either mode (Pi keeps `ctrl+shift+up` / `ctrl+shift+down` for its own prompt navigation). The collapse header stays visible; the row-range hint shows when more content is available. Task data and the agent's plan remain complete.

### Gentle Stats

It combines the active home's `sessions` directory with your regular Pi home's (`~/.pi/agent/sessions`, or the custom `PI_CODING_AGENT_DIR` that `gentle-shell` recorded as `GENTLE_SHELL_USER_PI_HOME` before isolating). The same directory reached twice counts once, and a session present in both homes counts once (the copy with more usage records, then the most recent one). Nothing new is stored. Subscription limits stay in `/gentle:usage`.

- **Models**: tokens, cost, messages, and share per model, with a share bar.

- `Tab`/`shift+Tab`, `←`/`→`, or `1`/`2`/`3` switch tabs; `r` cycles all time, last 7 days, and last 30 days; `s` toggles all projects and the current project (sessions started in this cwd); `q` or `esc` closes. Header tabs, `[× Close]`, and the footer hints are clickable.

- Only top-level session files are read: subagent runs are not included, and the panel says so. The first opening scans every file; later openings reread only files that changed.

### Gentle Design

`/gentle:design <brief>` asks the session model to design the brief with the bundled `gentle-design` skill. It works with any provider: the model writes several clearly different directions (3 by default), each labeled with its tradeoff, as self-contained HTML artboards under `design/<slug>/`, plus a `design.json` manifest. Artboards inline their CSS, JS, and SVG and use system fonts, so they open offline in any browser. When `design/system.md` exists, the skill follows its tokens. Ask for changes to one artboard and only that file changes; "save and try a different approach" adds an artboard and keeps the others.

You do not need the command: ask in plain language for a screen, mockup, landing page, or a few visual directions, and the session uses the gentle-design skill by default with any provider. After it writes or changes a design under `design/<slug>/`, the model opens the canvas on it (or refreshes the running one) through the `gentle_design` tool, unless you ask it not to. The same tool lists the designs and their artboards, shows whether the canvas is running and at which URL, stops the canvas, and starts the handoff of an artboard (`<slug>/<artboard>`) to the project's real stack, using exactly the text `/gentle:design implement` sends. Briefs and the design-system sync go through the skill itself. The `/gentle:design` subcommands remain available as optional shortcuts, and they share the same canvas server as the tool. Delegated subagents (`GENTLE_PI_AGENTS_CHILD=1`) do not get the default design flow.

The canvas opens in navigation mode: the mouse wheel and trackpad pan or zoom the canvas, even over an artboard, a drag on the empty canvas pans it (a drag on an artboard moves it; see **Layout**), and Ctrl/Cmd + wheel zooms. Hovering an artboard shows "Click to use this design"; clicking it enters focus mode, which shows that artboard at 100% as wide as the window (**Desktop**, see **Sizes**; an artboard designed wider than the window keeps its width and is drawn smaller to fit, with the zoom showing how much) and lets it own the pointer and keyboard, so its own scrolling, hovers, buttons, and inputs behave like the real page. While an artboard is in focus, it keeps 8 px from the window's edges with a 48 px band below it for "Back to canvas", the comments panel hides to make room, the other artboards are hidden, the canvas does not pan or zoom, and an artboard taller than the window scrolls inside its frame. To return to navigation mode, press the floating "Back to canvas" button or `Shift+Esc`, which works even while typing inside the artboard; plain `Esc` stays with the design, and the previous zoom, position, and comments panel are restored. Comment mode keeps working in both modes: a click picks an element instead of entering focus mode.

The arrangement is off inside an artboard, in Compare and when no board shows, and in Comment mode a drag on an artboard pans instead of moving it, so a click still picks an element. `Space` held on **Row**, **Column** or **Grid** just clicked pans too; a button reached with `Tab` keeps `Space` for itself. - **Sizes**: the **Preview size** button in the top bar, after **Row**, **Column** and **Grid**, shows the open artboard's size with its icon, name and `<width> × <height>` (`Desktop 1440 × 900`); it works on an open artboard only, so outside focus mode it is disabled and its tooltip says to open an artboard. A width out of range keeps the menu open and says which numbers it takes. A size resizes the artboard's frame at 100% without reloading it, so the design's own media queries respond; a size taller than the window is clipped like a tall artboard, and one wider than the window keeps its width and is drawn smaller to fit. **All sizes** shows the open artboard at Phone, Tablet and **As designed** (the artboard's own size in `design.json`) side by side below its title, each in its own iframe at its true width so the design's media queries apply, all drawn at one scale that fits the window (each label names the size and the scale); live reload reloads every frame. Comment mode and pins work at every size and in every All sizes frame: a pick opens the comment box beside the element in the frame it was made in. A frame whose page is wider than it shows an **Overflows** chip at its bottom right, whose tooltip says the content is wider than that many px; the open artboard's own frame shows it only at a single size. A comment made at Phone, Tablet, a custom width or in an All sizes frame records that size unless it is the artboard's own; Desktop records none, since its width is the window's. Its card in the comments panel shows the size it was made at (`Phone 390 × 844`, `Tablet 820 × 1180` or `<width> × <height>`). Leaving focus mode, or opening another artboard, restores the artboard's own size and closes All sizes.
- **Minimap** (bottom right of the canvas): every board drawn small where the layout puts it, the chosen artboard in the accent color, and the visible area outlined; click or drag in it to move the view there. `M` (a single key you can change in **Keyboard shortcuts**) shows or hides it; it hides inside an artboard and in Compare. The minimap is pointer-only (a picture to screen readers); from the keyboard the arrow keys pan the canvas, `+` and `-` zoom and `0` fits every board.
- **Export**: every design artboard (not the Design system board) has a **⋯** button beside **Implement this** that opens a menu with **Export as PNG**, **Export as PNG at 2×**, **Export as PDF** and **Download HTML**, with the usual menu keys (arrows, `Home`, `End`, `Enter`, `Esc` back to the button, `Tab` or a click outside to close); a pan or zoom closes it. **Export as PDF** prints the artboard alone, at its size in `design.json` as one page with no margin, through the browser's print dialog (choose *Save as PDF*; if the artboard file cannot be read or the dialog cannot open, the status line says so); it works in every browser, and content below that height is not printed. **Download HTML** saves the artboard file exactly as written in `design/<slug>/`, without the inspector the canvas server adds. **Export as PNG** and **Export as PNG at 2×** use the browser's own tab capture: the browser's selector opens at once and the status line asks you to choose the canvas tab in it, then, for one frame, the canvas hides its own controls and, inside the artboard, the selected comment's outline and Comment mode's hover outline, places the artboard at 100% in the window's top left at its size in `design.json` (Desktop's own width, whatever preview size was open), grabs the frame, stops the capture, restores the open artboard, its preview size, the view (fitted again or re-centered when the window changed size meanwhile), Comment mode and that outline, and puts the keyboard focus back on **⋯**. While one PNG export runs, another one is ignored. It downloads `<artboard>.png` or `<artboard>@2x.png`; at 2× it uses the screen's pixel density or upscales, and says so. The window must be at least as large as the artboard (full screen, `F11`, helps); otherwise the export stops and names the size it needs. It also stops with an explanation on the status line when the capture API is missing, permission is denied, a window or a screen was shared instead of the tab, sharing stopped before the frame was grabbed, a `design.json` reload removed the artboard meanwhile (a reload that keeps it, before the capture starts, exports the reloaded artboard), or a reload or **Back** replaced or closed the artboard while the frame was being grabbed. Browsers that only offer windows or screens, such as Firefox, cannot export this way; Chrome and other Chromium browsers offer the tab. When export is not possible, use the browser's own screenshot tool. **Export as PNG** contacts no server; **Export as PDF** and **Download HTML** only read the artboard file from the canvas server. In every case nothing is uploaded and nothing is written under `design/`.
- **Tokens**: with **Technical details** on (in **Settings**; off by default, saved in this browser under the `localStorage` key `gentle-design:technical`, and off for a browser that blocks storage), Comment mode shows a panel beside the frame of the element under the pointer: in the overview, in focus mode for the open artboard only (at any size, also in every All sizes frame), never on the Design system board and never while the comment box is open; artboards measure the element under the pointer only while Technical details is on. It shows the element's selector and its computed text color, background (walked up to the first opaque ancestor, translucent layers composited), font family and size, line height, margins and paddings, border radius, and the WCAG contrast ratio of the text on that background. Each value shows the `design/system.md` token it matches, or **⚠ no token** with the nearest one: colors by perceptual distance (OKLab), sizes by numeric distance. Contrast under AA (4.5 : 1, or 3 : 1 for large text: 24 px or more, or 18.66 px bold) is flagged; the ratio is shown to two decimals without rounding up. The canvas reads the tokens from the canvas server (`GET api/system/tokens`: each table row of `design/system.md` whose first cell is a backticked custom property, read-only, at most 256 KB and 500 tokens) when it starts and again when `design/system.md` changes; without that file, or for a kind with no tokens, the panel shows the values and the contrast without a comparison (and says when `design/system.md` is over 256 KB or could not be read), a read that fails keeps the tokens it had, and an open panel compares with new tokens at once. **Ask the agent to fix** opens the comment box on that element, prefilled and editable, with the flagged values and their nearest tokens, and follows **Send now** or **Collect** (and the size it was made at, in All sizes or at another preview size); it is disabled when nothing is off the system. **Copy** copies what the panel shows: the element, its selector and each row as `label: value` on its own line (with a fallback when the browser blocks the clipboard). Once a panel shows, it follows another element only after the pointer rests on it (250 ms), so the pointer can cross the artboard to the panel's buttons, and with the pointer on the panel nothing changes. The panel stays while the pointer or the keyboard is in it and goes shortly (300 ms) after the pointer leaves the element or keyboard focus leaves the panel; `Esc` in the panel closes it, with focus back on the canvas and Comment mode still on. It closes when Comment mode, focus mode, the preview size or the design changes, on a pan or a zoom, when the open artboard is re-centered (a layout change or a resize), when its frame goes (a `design.json` reload) and when Technical details goes off. These are heuristics: an element with a background image or gradient has no known background, and the match uses computed values, not the CSS that produced them.
- **Quality** (accessibility checks): the panel has two tabs, **Comments** and **Quality**, each with its count (open comments; problems found, shown once an artboard has reported), and the arrow keys, `Home` and `End` move between them; **Partial implementations** stays at the bottom in both. Each design artboard's own frame checks its page once it loads and again after a resize, once the size settles: text with contrast under AA (4.5 : 1, or 3 : 1 for large text; translucent text and every opacity on the element and its ancestors, which fades the text and its background together over what lies behind, are composited down to the page; text with an image or gradient showing through behind it is not judged, since its background is unknown), rendered `img` without an `alt` attribute (an image inside a `display: none` parent is skipped; one not loaded yet is not), form fields without an accessible label (`label[for]`, a wrapping `label`, `aria-label`, `aria-labelledby` or `title`), and heading levels that skip. Target sizes are listed as advice and never count: interactive elements (`a[href]`, `button`, `input`, `select`, `textarea`, `[role=button]`, focusable `[tabindex]`; inline links and disabled controls are skipped) smaller than 24 × 24 CSS px (the WCAG 2.2 target size minimum, which a smaller target also meets with enough space around it, and the check cannot measure that space), and those under 44 × 44 px. The Design system board and the All sizes frames are never checked. **Quality** has a group per design artboard reading `Accessible ✓`, `N checks` or **Not checked yet**, a card per finding as the artboard reported it, in the canvas language (the artboard sends each finding in English with a key and its values, from which the canvas words it; a finding it cannot word that way shows the English it came with), with **Problem** or **Advice** in words, and the checks that passed listed once. **Show** scrolls the artboard's page to the element, centers it and draws a ring around it on the canvas (never inside the artboard's page), labeled with the check's title and the same size on screen at any zoom; under 100% it also zooms in, to 100% or to the zoom at which a large element fits the view, never out, and in focus mode the artboard stays where it is. The ring follows the element as its page scrolls (in All sizes, in the frame as designed, where it is drawn), and is not drawn while the element is scrolled out of its frame. One ring at a time: `Esc` (after the comment box, Compare, a menu or a dialog, and before the selected artboard), a click elsewhere on the canvas, another **Show**, a reload of its artboard, another size, leaving All sizes or another design clears it, with the element's highlight in the artboard, while a drag that pans keeps it; an export never includes it. A finding whose element is hidden or off-screen (such as a skip link) says so, and its **Show** centers the artboard without a ring. **Ask the agent to fix** opens the comment box on that element (with its text, as a click in Comment mode records it), prefilled and editable, and follows **Send now** or **Collect**; the comment records the preview size the finding was found at, even after you change the size and before the artboard's next check arrives (a check the page made before it heard of a new size is ignored). The checks run inside the artboard's own frame, so they describe the artboard at the size it is shown, and they are heuristics, not a full audit: they miss keyboard, focus-order, motion and screen-reader problems, each list is capped (20 problems and 10 advice items per check, with the full count reported), and a page with more than 3000 elements is checked only up to its 3000th, so its counts cover that part only.

- Comments: turn on Comment mode, click an element in an artboard, and type a comment. Every comment is saved in `design/<slug>/comments.json` with its artboard, CSS selector, text excerpt, date, and status (`open` or `resolved`), so any agent or later session can read it.
  - **Send now** (the default) also sends the session one message with the design, the comment id, the artboard file, the selector, the excerpt, and the comment; while the agent is busy, it is queued as a follow-up.
  - A comment can carry one screenshot, useful for what only shows between states, such as an animation or a transition: paste an image into the comment popover, drop one onto it, or use **Attach screenshot** (PNG, JPEG, WebP, or GIF, up to 5 MB). It is saved as `design/<slug>/.screenshots/<id>.<ext>`, named in the comment's optional `screenshot` field, shown as a thumbnail in the Comments panel, and reaches the session as an image attached to the comment message (a Send all message attaches at most 6; the rest are named for the read tool).

  - A numbered pin marks each commented element and follows zoom and pan. The Comments panel lists open and resolved comments; selecting one highlights its pin and scrolls the canvas to it, and each comment can be resolved or reopened there. A comment whose element no longer exists shows as **Detached**.

The canvas updates live when the file changes, whoever wrote it. - `/gentle:design stop` closes the canvas; quitting or replacing the session closes it too. There is one canvas server per session, and a second `open` reuses it.
- `open` reuses the canvas tab that is already open: while a canvas page is connected, the command and the `gentle_design` tool tell that page to show the requested design and reload it from disk (keeping zoom, pan, and focus mode when it is the same design), and report "Design canvas refreshed" with the URL. The browser opens a new tab only when no canvas page is connected, for example after you closed it or when the server had to start.
- `/gentle:design sync` (it takes no arguments; extra words warn and send nothing) asks the session model to capture the project's design system with the same skill (queued as a follow-up while the agent is busy). It reads, and never edits, the project's design sources: CSS custom properties (`:root`, `@theme`, `[data-theme]`), the Tailwind config or v4 `@theme`, component library folders, existing token files, and fonts. It writes two files:
  - `design/system.md`: colors (token, value, usage), typography, spacing, radius, shadows, and component rules, each with the path it came from. Later design runs use only these tokens, and the skill checks every finished artboard's colors and fonts against them and fixes any deviation.
  - `design/system.html`: a self-contained 1440 px artboard that renders those tokens and the core components.

  When the project has no design sources, the model says so and proposes a minimal starter system instead of inventing project tokens.

  You rarely need to run `sync` yourself. Before a new design, the skill calls the `gentle_design` tool's `list` action, which reports the project's design sources (the first 20 paths and a total) and the state of `design/system.md`. When the project has design sources but no `design/system.md`, the model syncs first, says so in one line, and then designs with those tokens. When the project has no design sources, it designs freely. When a source changed after `design/system.md` was written (by modification time), the model names it, says the tokens may be outdated, and offers to sync again; it re-syncs only with your OK. A design source is a `tailwind.config.{js,cjs,mjs,ts}`; a `.css`, `.scss`, or `.pcss` file that uses `@theme` or declares a custom property in a `:root` or `[data-theme]` rule; a `.json`, `.js`, `.ts`, or `.css` file whose name has `tokens` as a whole word (`tokens.json`, `design-tokens.ts`, `theme.tokens.css`; never `token.ts`, `refreshToken.ts`, `tokenizer.ts`, or a `.test`/`.spec` file); or a `theme.js`/`theme.ts` that exports a `colors` key. The detection walk skips `node_modules`, `dist`, `build`, `out`, `coverage`, every dot-directory (such as `.git`, `.next`, `.worktrees`), and the project's own `design/` folder; it does not follow symlinks, goes at most 6 directories deep, stops after 5000 files, and reads at most 256 KiB of each file.
- When `design/system.html` exists, the canvas shows it as the first board of every design, labeled **Design system** with "Project tokens (design/system.md)", and reloads it when the file changes. Comment mode does not apply to that board (its tooltip says so): change the system by updating the design sources and running `sync` again.
- `/gentle:design implement <slug>/<artboard>`, or **Implement this** on an artboard's header in the canvas (after a confirm step; never on the system board), sends the session one handoff message, queued as a follow-up while the agent is busy. Both send the same text: the artboard path, title, and tradeoff; an instruction to build it in the project's real stack with the artboard as the visual spec, mapped to existing components rather than copied; `design/system.md` as the token source when it exists; and every open comment on that artboard, to apply and then resolve with `gentle_design_comments`. An unknown design or artboard warns with the valid `<slug>/<artboard>` values and sends nothing. An invalid `feature` link in `design.json` is reported as a warning, and the handoff goes out unlinked. The handoff itself commits nothing.
- ODD link: a design that comes from a tracked ODD feature records it in `design.json` as `"feature": "odd/tasks/<feature>.md"`, and the skill appends a Log entry naming the design to that document; small, untracked work has no `feature` and stays standalone. The canvas top bar shows **Feature: <path>** for a linked design, and the handoff asks to track the implementation in that document instead of sizing it from scratch. Only a relative `odd/tasks/<name>.md` path is accepted; any other value is ignored and reported as a warning in the canvas.
- Handoff state: every handoff (the canvas button, the command, or the tool's `implement`) is recorded in `design/<slug>/handoffs.json` before it is sent, and the handed-off artboard becomes the design's **chosen** direction: its header shows a **Chosen** badge and an accent frame, and the other artboards show **Alternative**. Handing off another artboard moves the mark. After **Send**, a toast confirms it, and the artboard's header shows **Queued** (the agent was busy) or **Implementing…** (it was idle), then **In progress** and **Implemented ✓** as the agent reports them with the `gentle_design` tool's `handoff` action, which the handoff message asks it to call. The canvas updates live, the badge names the linked feature document, and `list` reports each design's chosen artboard and handoff states. When the agent marks an artboard implemented with the `previewUrl` of the running app, **Compare** shows the artboard and the app side by side at the artboard's size, at 100%, with **Scale to fit** when the pair is wider than the window; exit with **Back to canvas** or `Shift+Esc`. The preview must be an `http`/`https` URL on `localhost`, `127.0.0.1`, or `[::1]` (any port, no credentials, at most 2048 characters); the tool and the server refuse anything else. Prefer `localhost` or `127.0.0.1`: CSP has no IPv6 source form, so browsers do not frame a `[::1]` preview, and Compare says so and offers the new tab. An app that refuses to be framed (`X-Frame-Options` or `frame-ancestors`) still opens with **Open in new tab**, which the Compare view always shows.
- Implement only this: when the directions share a piece you already want in the app (a side menu, a card), build that piece on its own while you keep choosing. In Comment mode, click the element and choose **Implement only this** in the comment popover, between **Cancel** and **Send**; the field becomes an optional note (at most 2000 characters). It sends the session the artboard, the element's selector and excerpt and the note, and does not choose a direction: the chosen artboard and the alternatives stay as they are. A toast and the status line say **Sent** or **Queued** (a busy agent gets it as a follow-up), and a refusal shows its reason on the popover's message line. The button is disabled, with the reason in a note under the buttons, when no Pi session is behind the canvas. **Partial implementations** (with its count), at the bottom of the comments panel and hidden while the design has no parts, lists the design's parts live from `parts.json`: the artboard, the state in words (**Sent**, **Queued**, **In progress**, **Implemented ✓**) and since when, the excerpt, the agent's note, and **Show**, which opens the artboard and highlights the element in every frame of it (also in All sizes). A part still **Sent** or **Queued** has **Remove**, which asks first, inline, because the agent can no longer report on a removed part; when the agent took the part up meanwhile, or a failed delivery already took it back, nothing is removed, the list reloads and the status line says why.
- Parts: the canvas server's `POST api/designs/<slug>/implement-part` hands one element of an artboard to the session without choosing a direction. Each part is recorded in `design/<slug>/parts.json` (never `handoffs.json`) as `sent`, then `in_progress` and `implemented` as the agent reports it; a repeated `in_progress` report keeps the time the part was first started. `parts.json` holds at most 1 MiB: a part or report that would make it larger is refused (`409 parts-too-large` on the canvas routes) and the previous file stays as it was. A part the agent never reports can be cleared with `POST api/designs/<slug>/parts/remove` and `{ "id": "<part id>" }`: it removes only a part still `sent` (queued or not) and answers `200 { "ok": true, "id" }`. A Remove that arrives while that design is still delivering a part waits until the delivery settles, so a part is never removed while its message is on its way to the session; once a failed delivery has taken the part back, the Remove answers `404 not-found`. A part in progress or implemented is `409 part-not-sent`, an unknown id `404 not-found`, a malformed id `400 invalid-part`, and an unreadable `parts.json` `422 invalid-parts`; a refusal writes nothing. Every change to `parts.json` reaches open canvas pages as a live change event.

The canvas server binds `127.0.0.1` on a random port and needs a random per-server token in every URL. It rejects any `Host` other than its own loopback address, accepts every write (comments, Send all, resolve/reopen, Implement, parts) only with its own `Origin` (`http://127.0.0.1:<port>` or `http://localhost:<port>`), a JSON body, and bounded lengths, keeps at most 500 comments per design, and serves only files under `design/` in the session cwd (design folders, plus exactly `design/system.html` for the system board), resolved by real path so neither `..` nor a symlink can escape. Artboards run in iframes sandboxed without `allow-same-origin`, so they cannot read the canvas or post comments themselves. The canvas may frame only loopback origins (its `frame-src`), and the Compare preview frame keeps its own origin (`allow-scripts allow-same-origin allow-forms allow-popups`, never top navigation) only because it is another origin than the canvas: the canvas refuses a preview on its own port, and sends no referrer, so the app never sees the token. No other network traffic is involved. The server and the tool write `comments.json`, `handoffs.json` and `parts.json` one at a time through an atomic replace, and never overwrite a file they cannot parse.

### Gentle Music

`/gentle:music [mood]` hands the terminal to the [gentle-stream](https://github.com/Gentleman-Programming/gentle-stream) player, like Pi's external editor, passing the mood and the session model. In the player, `b` returns to Pi with the music playing and `q` returns and stops it. `/gentle:music next`, `pause`, `play`, `stop`, and `status` control the music without leaving Pi. Quitting Pi after using the command stops the music. gentle-stream runs from `PATH`, or through `uvx`/`uv` when it is not installed. On native Windows the player is not available yet (it needs POSIX; WSL works), so the command only says so. A bundled Gentle Shell on macOS or Linux without any of them offers, with your consent, to install the player inside its own folder: a pinned, checksum-verified uv 0.13.6 in `runtime/`, and the uv-managed Python 3.13 and gentle-stream in `music/` (about 150 MB to download, about 210 MB on disk). A pnpm or npm install keeps the manual install hint. See [Gentle Music](gentle-music.md).

### Bridge providers

Idle Claude Bridge continuation uses the normal user-prompt lifecycle so prompt preparation and tool declarations are retained. Gentle Agents hides only its exact, uniquely generated reserved wake in Pi's interactive transcript; child result and query cards remain visible. Native providers keep their hidden `display: false` custom wake. Pi gives custom messages to the model with the user role, so the native wake carries the same "not written by the user" label as the Bridge wake and asks for a reply in the language of the human's own last message, never the language of the notification or of the subagent output. The Bridge wake text is unchanged because persisted wake identities embed it. That label alone does not hold in long sessions, where the human's message sits far up the transcript or has been compacted away, so the harness also anchors the reply language itself: it records the human's own typed input (interactive or RPC, never extension-sent text such as Bridge wakes) and, when the primary session is about to answer right after an automated message, adds one hidden `gentle-pi.reply-language` note quoting the start of that input. The note is added only when the request ends with an automated message, so a plain tool round adds nothing, and it is persisted once per such message, so requests stay append-only for the provider's prompt cache; child sessions never receive it.

The reserved identity is stored once per session as a non-context custom entry and reconstructed on reload/resume, including identities on abandoned branches. It is session-owned: switching sessions releases the previous identity. Ordinary text quoting the old notification, prefixes, substrings, and whitespace variations is not hidden. Pi's transformer exposes no author/message ID, so an exact copy of the current reserved identity is indistinguishable from its generated wake.

This is **TUI-only suppression**: the generated user-role message remains in session history, model context, and RPC. It does not fix the SDK's idle custom-message lifecycle. Older runtimes without the Markdown transformer API, or failed identity persistence, retain visible continuation and emit a warning rather than dropping the wake. Existing unreserved wakes are not retroactively hidden.

The Gentle AI harness (ODD workflow, identity, review contract) and the open-tasks block are appended to `before_agent_start`'s `systemPromptOptions.appendSystemPrompt` instead of being returned as a replacement `systemPrompt` (gentle-shell#1485). Provider bridges such as `pi-claude-bridge` forward only those structured sections after their own preset and drop a returned `systemPrompt`, so this route reaches every provider, bridged or not.

### Empty review scope after acknowledgement

After acknowledging a committed candidate, a selectorless STATUS may inspect the empty workspace and return `empty_candidate_base_ref_required`. The `blocked` label describes that candidate selection request; it does not establish that the earlier review failed or remains open. To check the previously acknowledged candidate, use ASSESS with its original `baseRef` and `committedOnly: true`, and rely on the returned native `candidate.consumed` evidence. Do not infer closure from the empty workspace or repeat the acknowledgement.

Set `GENTLE_PI_SHELL=0` to keep pi's built-in footer and editor.
