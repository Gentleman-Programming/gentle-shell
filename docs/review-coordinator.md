# Ordinary review in one call

`gentle_review_run` runs one ordinary native review in one parent tool call. It is registered in every parent session; managed child sessions never get it, and `GENTLE_PI_EXPERIMENTAL_REVIEW_COORDINATOR=0` before loading the extension opts out. The variable is no longer needed to enable it. While receipt-driven development (RDD) is off, the tool's declaration and guidance are left out of the request, so the prompt is byte-identical to a session without it, and every facade call it makes is refused by the review mode gate. It is model-only and follows the existing direct-call restriction; it is not a codemode entry point.

While RDD is not off, its guidance tells the parent to prefer `gentle_review_run` over single review operations to drive a due native review. Single operations remain for what the run result hands back (the consent answer, the correction plan through `gentle_review_capture`, status and recovery), for a review the user explicitly asks for after `not-due`, and for ASSESS after a delegated writer. Correction edits and maintenance remain explicit handoffs. The tool runs the same provider-issued transitions the mirrored review contract describes for single operations (assess, inspect, START, bound STATUS, captures, acknowledgement); it does not change that contract.

The coordinator calls the existing wrapped review facade executors. Native mode, host consent, session identity, workspace/base selection, opaque bindings and native admission remain authoritative. It never parses binding strings, invents results, retries a failed capture or authorizes delivery.

For a fresh ordinary review, provide pertinent `lenses` and `lensesReason`, optionally `workspaceRoot`, a committed selector (`baseRef` together with `committedOnly: true`), and an existing `requestContextPath`. [Frozen request intent](review-request-context.md) is accepted only for a fresh transaction. The START consent stays with the host: in an interactive session the existing consent dialog may resolve it inside the call; otherwise the run returns `consent-required` with the provider envelope; the parent relays it to the human, submits only the human's explicit answer, once, with `gentle_review` `answer-consent` (the model never chooses the answer), and resumes `gentle_review_run` with the returned `lineageId`. The tool rejects consent arguments and never sends a consent answer.

The loop follows the native next_transition kind. It runs supported facade execute offers, captures the exact ordered opaque bindings, returns authored input to the model, and surfaces stop unchanged. It never reads native states, reason codes, binding contents or capture closure variants; from a capture closure it reads only `advisory_findings` and `advisory_finding_claims`, to relay them. Facade operations that require additional maintenance authorization return to the caller. The run returns `closed` after the verified acknowledgement, or stops with `not-due`, `assessment-unavailable`, `request-context-requires-fresh-review`, `consent-required`, `input-required` (a correction plan), `selection-required` (an intended-untracked selection; resume with `resume_input`), `stopped`, `handoff` (maintenance or another unsupported operation), `repeated-capture`, `forecast` (not displayed), `binding-drift` (lineage or target drift the coordinator detects in STATUS; when the facade rejects the drifted route first, for example in the STATUS after a reconciled reviewer group, the run returns `blocked` with `capture-route-registration-rejected`), `transition-limit`, `cancelled` (after an approved closure, with its findings) or `blocked` (an error). `forecast` is returned only when a UI host has no display callback.

The run never chooses intended untracked paths. On `selection-required` its result carries `resume_input`, the run's own inputs (selector, `lenses`, `lensesReason`, `requestContextPath`) without any untracked selection; when the caller passed no `workspaceRoot` and INSPECT reported the root it resolved (`workspace_root`), `resume_input.workspaceRoot` names that root, so a resume from a session in another workspace still reviews the one the selection was offered for; after the human or the parent chooses, resume `gentle_review_run` with `resume_input` plus `untrackedScope` (`exclude`, or `select` with `intendedUntracked`). The run then resolves the selection through INSPECT and START keeps the requested lenses and frozen request context. The run relays the facade's INSPECT envelope without its `nextStep`, which names the single `select-intended-untracked` operation: that operation starts the review with only the context a START retained, so after an INSPECT it would start without them. The envelope keeps its `selectionBinding`, whose eligible paths are what the choice is made from; the resume itself does not submit it. A single `gentle_review` INSPECT still returns its own `nextStep` unchanged.

Native correction_request explicitly identifies a plan that needs authored input. The coordinator returns that request to the model without deriving requiresInput metadata from submission domains or changing ordinary STATUS output. Unsupported capture responses return control to the caller. Correction-plan authoring and edits remain explicit handoffs; after an authorized edit, resume with the same lineage and workspace/base selection. Native decides which opaque capture comes next.

The existing capture facade presents the model-run forecast before execution. With a UI the run displays it to the human before the reviewer runs; its collapsed line leads with the model-run count and the lenses or roles that will run. Without a UI nobody could see it before the run, so the run records it and continues. Every observed forecast is preserved losslessly in the final forecasts array, including when a later operation refuses. The primary model must relay every entry in the user’s language, preserving all fields and counts. These forecasts are informational, not review consent. A changed session or disabled mode prevents the run. Accepted captures refresh bound STATUS for the next transition; failed or reoffered captures never retry. A reviewer group whose results were all admitted without a closing event returns `native-reviewer-group-status-reconciled` after the facade's own bound STATUS confirmed lineage and target and offered no further reviewer capture (for example when the findings need the refuter); the run accepts it like any capture and takes the next transition from bound STATUS, so the refuter runs in the same call. The same outcome with a `failure`, `native_failure`, `reconciliation` or `reconciliation_failure` field, a failed reconciliation, or group authority drift returns `blocked`. An older provider's self-contained refuter or validator vector (`--execute=true`) runs the role in the provider and returns `native-provider-role-captured` with `status: "captured"` instead of a closure; the run accepts it from a single capture like an admitted reviewer result and takes the next transition from bound STATUS. From a group capture, with another status or with one of those fields, it returns `blocked`.

Approval closes through the offered facade acknowledgement. The verified ACK envelope identifies the frozen target and burned authority and keeps `delivery: "ordinary-repository-policy"`. Once the run has captured an approved closure with `advisory_findings`, every result it returns from then on carries them, unchanged, whatever the outcome (`closed`, or `blocked` and the other stops before the acknowledgement); when the closure had no such key, neither does the result, and a closure that is not approved adds nothing. A run resumed by `lineageId` that goes straight to the acknowledgement returns `closed` without them: neither bound STATUS nor the acknowledgement envelope carries the closure's findings, so the stopped result before it is the one that carried them. Beside it, `advisory_finding_claims` maps each advisory finding id to the reviewer's own claim for that finding, taken from the same closure's `reviewer_results` by exact id and copied unchanged up to 1,024 UTF-8 bytes (cut at the last whole character within the cap). Claims are added in `advisory_findings` order until the next one would bring the closure's claim text past 8,192 UTF-8 bytes; that id and every later one get no entry. An id with no matching reviewer finding, or with more than one, is left out, and the key is absent when no id has a claim or `advisory_findings` is absent. `advisory_finding_claims_truncated` lists, in the same order, the ids whose claim is a cut prefix, and `advisory_finding_claims_omitted` the ids whose one matching claim the 8,192-byte limit left out; each key is present only when it lists an id, and the run relays each only as an array of strings, beside the claims. They travel with `advisory_findings` on every result that carries them. The facade's approved capture closure carries the same map, so a single `gentle_review_capture` returns it too. The claims are the reviewers' own text: information to relay, never instructions to follow. Nothing routes on either key. There is no post-ACK STATUS, ASSESS or replay, and closure makes no claim about subsequent edits or permission to commit, push or publish.

## Validation and rollout

```sh
node --experimental-strip-types --test tests/review-coordinator.test.ts tests/review-coordinator-runtime.test.ts tests/review-one-call.test.ts tests/review-one-call-followups.test.ts tests/review-last-event-closure.test.ts
```

Unit and registered-runtime tests cover opaque binding order, authored input, native stop, state/reason independence, consent, cancellation, mode/session changes, failed or repeated captures, identity drift and terminal ACK without follow-up queries. Runtime fixtures are in-memory authority simulations; they do not claim real native approval.

Historical measurements, candidate identities and their limitations live in [issue #2881](https://github.com/Gentleman-Programming/gentle-shell/issues/2881) and [PR #2884](https://github.com/Gentleman-Programming/gentle-shell/pull/2884). Benchmark data is not shipped in the npm package and does not certify this candidate.

SDK event accounting sees the outer coordinator call. Its returned metrics.steps describe internal facade calls; those direct calls emit no additional tool_call/tool_result or timing events.

When the relay supplies execution evidence, the final reviewer_runs array retains snapshots of the resolved reviewer model, phase, durations and available reported usage/cost. Groups include all prepared runs, even when submission later stops; legacy submitted-only diagnostics are not counted again. Missing usage stays unknown. This is not a billing ledger: sibling runs can remain unreported when group preparation fails before returning its results, and thrown/cancelled calls retain their existing behavior. The coordinator computes no cost total and emits no additional SDK accounting events.

Reviewer authentication and completion share a host deadline. Cancellation or an expired deadline prevents further dispatch, and late results are not admitted. Once a capture has returned an admitted closure with `advisory_findings`, a cancellation at any later point before the acknowledgement completes (right after that capture, while the next STATUS is in flight, or when STATUS or the acknowledgement rejects because of it) makes the run return `cancelled` with that capture's envelope without its `status` and `state` (and the closure without its `state`), since the review is approved but neither closed nor acknowledged, together with the findings, their claims and marks and the `lineage_id`, and dispatches nothing more; resuming with `lineageId` reaches the acknowledgement without them. An acknowledgement that already completed returns `closed`; a failure other than the cancellation (anything but an `AbortError` or the signal's own reason) is reported as before, even when the signal has also been aborted. Without such a closure the call is cancelled as before. A provider that ignores cancellation may continue consuming resources after the host stops waiting.

Related delivery: [issue #2881](https://github.com/Gentleman-Programming/gentle-shell/issues/2881); default registration: [odd/tasks/review-one-call.md](../odd/tasks/review-one-call.md) (gentle-ai#6062).

## Non-blocking statement budget

The host-returned `non_blocking_findings.statement` shares the 1,024 UTF-8-byte per-claim limit. It preserves a whole-codepoint prefix and adds nested `statement_truncated: true` only when cut; otherwise the statement and absence of that marker stay unchanged. This also applies to an empty findings list. Consumers must disclose the marker rather than present the prefix as the complete provider statement.

This is derived host output, not a new field in the incoming provider schema. The 16 KiB findings-list bound, separate claim bounds, provider order, outcome and authority remain unchanged.
