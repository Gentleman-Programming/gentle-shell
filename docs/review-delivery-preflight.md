# Host delivery preflight

Shell's host workflow now checks recognizable `git push`, `gh pr create` and `gh pr merge` calls before execution (issue #2997). This changes Shell's previous unconditional delivery bypass. It does not restore the provider's retired receipt/gate APIs or change its byte-pinned contract artifacts. The vendored `review-integration.md` remains an exact upstream snapshot; this document describes the newer Shell-owned ordering policy.

With RDD on, select the actual delivery slice through `gentle_review` assess with explicit `baseRef` and `committedOnly: true`. `workspaceRoot` selects its worktree. The host resolves that selector to a fixed commit before assessment; a confirmed committed-range assessment retains only that base commit in the existing session continuation registry. Invalid or unresolved selections leave the existing hint unchanged. No parallel registry, cached verdict, capture/confirmation state or stored HEAD snapshot is created. The native assessment is always fresh and compares that fixed base to current HEAD, including commits made since selection. This also covers assessments invoked by the coordinator. Committed-only delivery requests omit untracked selection flags because they require no untracked inventory.

After command authorization, each foreground call gets one assessment per selected repository, even for a batch such as `git push && gh pr create`. A shell wrapper alone does not block the call. Native `reviewDue: false` preserves ordinary policy. A due review requires following the facade transitions or an exact host-recorded human decline; caller-supplied outcomes grant nothing. HEAD/base and session checks around the fresh read prevent using a result that changed during admission. A new HEAD before admission is assessed automatically, without requiring another registration cycle.

Commands that change the candidate (commit, revert, switch, rebase, etc.) must finish before its delivery can be evaluated. Delivery through the background or monitor tools still needs a separate foreground call because the job can run after its preflight is stale; background waits without delivery remain available. Missing base, cancellation and unavailable native evidence remain concrete blockers. Dynamic or implicit directory changes and recognized inline Git/environment repository redirects (such as `--git-dir`, `GIT_WORK_TREE` or `env -C`) are unresolved targets: run delivery inside its repository or use literal `cd` or `git -C`. The host cannot infer a redirected target's RDD mode from the session repository. For resolved repositories, RDD off retains ordinary command policy. The check runs no review, consent answer, acknowledgement, mode change or network lookup, and does not authorize delivery.

This covers recognizable shell invocations, including common shell wrappers and substitutions. It is not a shell sandbox or an installed Git hook. Script files, arbitrary interpreter programs and external actors are outside its detection boundary. The caller owns the actual slice, every pushed ref and the PR/remote destination: checking a local candidate does not verify an explicit remote override, prove an arbitrary PR number matches local HEAD or prevent later remote edits after auto-merge scheduling.

Literal `cd` is resolved only in a direct leading `&&` chain without other control operators, including inside a supported shell wrapper. A later `;` or other control operator also makes the directory state ambiguous if the `cd` fails. `cd` in subshells, pipelines, background syntax or ambiguous conditional flow, and any `pushd`/`popd`, make the delivery target unresolved. Split those steps and issue delivery from the intended repository or use literal `git -C`; the host does not simulate shell directory state.

Recognizable scheduling and exported routing are checked as follows:

- Shell `&` applies to its whole and/or list or compound command, not merely the last segment. With RDD on, recognized delivery such as `sleep 30 && git push &` or `git push && echo done &` must be separated into a new foreground call before assessment. Scheduling metadata also follows supported wrappers and substitutions. Background work outside the delivery's list does not by itself mark a later foreground delivery asynchronous; resolved RDD-off targets retain ordinary policy.
- Literal exports of `GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR` or `GIT_NAMESPACE` make later delivery in that environment unresolved, including exports through same-shell `eval`. This is rejected before reading the session repository's RDD mode. Exports inside a subshell, background list or backtick substitution do not contaminate a later parent-shell delivery; a delivery within that same child environment still has an unresolved target. Separate routing changes from delivery and issue it from the intended repository. This is bounded recognition of literal shell forms, not general shell-variable evaluation.

The provider's assessment policy, including `under_budget`, remains unchanged. The companion provider report #6028 remains separate; this host change does not claim to resolve inconsistent outcomes between provider assessment and other hosts' Stop hooks.

Regression coverage uses the real Shell hook and isolated Git repositories with stubbed native answers, plus the real native client's request validation with a stubbed process adapter. It checks one assessment per delivery batch, zero added asynchronous Git reads when retaining a base (canonical selection now performs synchronous Git resolution), fixed HEAD/branch bases, foreground batching/wrappers/eval, asynchronous delivery lists, process-scoped exports, unresolved-directory rejection, candidate-changing boundaries, late HEAD/selector/session changes, cancellation, and native non-due/human-decline paths. An additional Bash probe uses an inert local function to confirm scheduling and export visibility; it executes no Git delivery. These checks do not perform a real remote push/merge or claim a complete live-model journey or production latency improvement.
