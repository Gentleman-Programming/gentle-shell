# Desktop RPC: list sessions and switch by id over Desktop RPC

Implements #3320 on branch `feat/desktop-rpc-sessions`. Delivery: single PR closing #3320. Test runner: `node --experimental-strip-types --test` (`pnpm test`), plus `pnpm run typecheck`.

## Specs

- S1 (#3320, Proposed outcome, verbatim): Two Desktop RPC methods, discovered through `capabilities`:
- S2 (#3320, Proposed outcome, verbatim): `list_sessions { scope?: "project" | "all", limit?: number (1–50, default 20), cursor?: string }` → `{ sessions: [{ id, name?, modified, messageCount?, firstMessage (≤ 200 chars), project (display name, never a path), current: boolean }], nextCursor? }`, newest first. It resolves the session directory exactly as the runtime does (custom `sessionDir` included). It never returns a file path, a cwd, or full message text.
- S3 (#3320, Proposed outcome, verbatim): `switch_session { id }` resolves the id through the owner (`findById`) and switches with the command context's `switchSession`. Errors: `not_found` when the id does not resolve in the requested scope, `invalid_request` for bad params, `sessions_unavailable` when no command context is bound. Switching to the current session is a no-op that answers `changed: false`.
- S4 (#3320, Proposed outcome, verbatim): A switch starts a new session, so the router's event `sequence` resets with the new session as it does for Pi's own `switch_session`; the docs state this.

- L5 (2026-11-16, coordinator, verifier blocker, verbatim): "Desktop requests sent while a `switch_session` is in flight never get an answer." "Required behavior: every request gets exactly one response per requestId." Root cause, observed in the real runtime: requests sent right after a switch are dispatched concurrently; those that reach the old instance before teardown settled after the router stopped and were dropped, and those Pi delivered to the replaced instance during the replacement threw on the stale ctx (`extension_error`) before any answer. Decision (the recommended design, extended to the second path): (a) the sessions bridge marks the switch in flight synchronously at dispatch, and a new router gate (`DesktopRpcRouter.setGate`) answers every other request, any method, with the retryable `session_switching` at once; (b) on the switch's `session_shutdown`, the new `DesktopRpcRouter.abandonPending` answers every request still waiting on an owner with `session_switching` (keeping only the switch's own requestId) and drops their late outcomes; (c) the publisher now extracts `ctx.ui` once at session start (Pi keeps extracted raw objects usable after replacement), and a switch-retired instance answers any later command `session_switching` through it without touching the stale ctx. Only the switch answers from the new session. Existing router behavior is unchanged when no gate is set (`tests/desktop-rpc.test.ts`). Docs state the in-flight behavior and the new error code.
