# Engram companion integrity across updates

Two Shell-side fixes found while closing the engram daemon work: (A) nothing verifies that the `gentle-engram` companion is compatible with the bundled Engram core before memory is wired to it, so an incompatible pair only surfaces as memory blocked for the whole session (engram#2346 / gentle-shell#3015); (B) `gentle-shell update --extensions` can detach the Shell-managed companion install.

Repo: `C:/Users/devel/dev/gentle-shell`. Branch: `fix/engram-companion-integrity` (off `main` after `e8a56a1a4`).

## Specs

S1 — "ok hay que fixear eso tambien" — referring to the gap established in this session: Shell has no companion-to-core compatibility gate; the only companion gate is the capability check `pkg.engram?.startupPolicy === 1`, so an installed companion may require a newer core than the one Shell publishes, and the mismatch is discovered only at runtime through the `runtime-contract` digest, blocking memory for the session (gentle-shell#3015).

S2 — "y otra cosa que hay que fixear es que actualizar con "gs update --extensions" no debe desvincular la instalacion manageada" — running the extensions update must not detach / unlink the installation that Shell manages.

S3 — User decision (this session), asked as: "Cuando el companion gentle-engram pida un contrato de core que el core disponible no cumple, ¿qué debe hacer Shell?" Answer: "Instalar y avisar fuerte" (warn-only) — Shell still installs the companion and warns loudly at setup and on every launch; memory may end up degraded and the human decides whether to update the core or the companion. Shell must not silently block memory as the only signal.

S4 — Verified gate evidence (real release binaries, this session): `GET /runtime-contract` on core 3.5.2 answers digest `4bf32703e111162b24073d090bec1c15c9120708587000bf595a07264e768672` (its windows zip sha256 matched the retired 3.5.2 pin exactly), and core 3.7.0 answers `0af9af176928e98562ab1396d3196efe582dd5d1c5d2c5f8f546ab4ed609810f`, the digest `gentle-engram` 0.7.0 requires (gentle-shell#3015). Both report `contract_id` `engram.pi-http-runtime/v1` and `revision` 1; only the digest differs.

S5 — The detach mechanism established by T1 must be addressed as S2 states: `migrateManagedEngramCompanion` un-pins `npm:gentle-engram@0.4.2` to bare `npm:gentle-engram` (bin/gentle-shell.mjs:357-362); Pi's extensions update replaces that with `gentle-engram@latest` (its package-manager skips only pinned npm sources); `ensureEngramCompanion`'s version check never fires for a bare source (bin:398-404); and the launch-time verification is skipped entirely when a `piSubcommand` is set (bin:2351). Nothing re-verifies the replaced companion.
