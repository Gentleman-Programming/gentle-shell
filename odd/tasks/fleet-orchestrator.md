## Specs

- **S1 — New launch mode with its own TUI.** User: "quiero que diseñemos una opción para que cuando tú abres lo que sería Gentle Shell, que además puedas agregar un nuevo parámetro, Gentle Shell. Orchestrator, y eso lo que te va a dar es la posibilidad de tener toda una TWI nueva, donde puedas hablar con un agente, pero que esta gente lidere múltiples sesiones de Gentle Shell, cada uno con su orquestador y su agentes."
  User (L42): "mejor que sea gentle-shell fleet el comando".
  Acceptance: `gentle-shell fleet` opens an interactive session whose agent is the fleet orchestrator; each member it leads is a full Gentle Shell session with its own orchestrator and subagents.
- **S2 — Single source of truth, fleet led by one orchestrator.** User: "es como un solo lugar de la verdad, donde yo hablo con esa gente para llegar a un objetivo y que el por detrás haga lo que tenga que hacer. Realmente lo que tenga que hacer, como una flota de agentes, liderado por un buen orquestador."
  User (L15): "yo podria con esto orquestar mucho mas tranquilo proque el orquestador es el que responde a los agentes por mi y me ayuda a llegar al objetivo."
  Acceptance: the human only talks to the fleet orchestrator; the fleet owns its members (spawn, prompt, steer, stop) and answers member questions on the human's behalf toward the objective, escalating to the human only what falls outside its authority. Boundary (accepted, L17): the fleet decides alone everything that serves the objective (choices between options, scope clarifications, plan approvals, "continue with X or Y", feedback to members); it always escalates (1) provider consent, credentials and security permissions, (2) destructive or irreversible actions (delete, force push, payments), (3) external publishing (posting, uploading, sending email or DMs, merging, releasing) unless the human granted a standing permission for that scope, recorded in the fleet document. User (L17): "esto es un lugar para vos no preocuparte por nada, un lugar para manejar TODAS tus sesiones de una". Members are not limited to code: any Gentle Shell session (e.g. publishing or channel work) can be a member.
- **S3 — Token efficiency grounded in the benchmarks.** User: "para pensarlo tambien recurda todos los benchmarks que hicimos y demas para la eficiencia y buen uso de consumo de tokens"
  Acceptance: the design applies the measured findings recorded in `## Log` L3 (lean fleet prompt, code-built digests instead of transcripts, event-driven wake, reused members, hard budgets and correction caps); F0 measures the real fleet and member prefixes.
- **S4 — Headless members, visible to the user.** User: "headless pero tenemos que poder ver a nivl usuario que esta haciendo cada uno"
  Acceptance: members run headless (Pi RPC) and the user can see, from the fleet TUI, what each member is doing (current task, todo progress, recent activity, waiting questions).
- **S5 — Fleet-level ODD document.** User: "tambien tendria wue haver como un odd.md" / "para hacer seguimiento pero de nievl general para ver el edtado de todo"
  Acceptance: the fleet maintains one general-level ODD-style document for its objective that shows the state of everything (objective, members, what each owns, status, blockers, log), kept current by code.
- **S7 — Fleet TUI design, TUI first.** User: "quiero que me hagas un diseño of how we have this in the Tui" / "la idea sería poter mediante una interfaz simple el chat con el orchestador, butas sessiones hijas y cómo se van desenvolvendo de una manera that's amigable and customizable" / "Hay mucha gente who trataban de hacer el famoso oficina that el orchestador in una sala aparte y luego tenemos diferentes subagentes trabajando y ves cómo trabajas, ¿no? Pero in este caso yo no quiero hacer ese concept, pero solamente con una ayuda visual de lo que piensa la gente. Pero que sea differente" / "Pero primero Tui, siempre."
  Acceptance: several clearly different TUI directions (simple chat with the orchestrator, child sessions and how they unfold, friendly, customizable, a visual aid of what the agents think, not the "office" metaphor), chosen by the user before T5 implements one; TUI first, a later migration to another version is out of scope now.
- **S6 — Design baseline (accepted in L4).** The architecture proposed in L2 with option 1 (headless members controlled by the fleet) is the baseline; changes to it are logged.
- **S8 — Adopt already-open Gentle Shell sessions (supersedes L18).** User (L58): "quiero agregar la capacidad de agregar sesiones ya abiertas de gentle shell para manejar". Decision (L59): "Adoptarla" — the fleet closes the interactive window and reopens it headless on the same session file as a member with full control (answer dialogs, steer, stop, protected relay).
  Acceptance: from the fleet, the human picks one running Gentle Shell session; that interactive session exits and the same session file continues as a fleet member; never two processes writing one session file. Decision (L60): "Sin confirmación (recomendado)" — the human's pick in the fleet TUI is the consent; the adopted window shows a notice, finishes its turn and closes itself. The pick is a human-only TUI action, never a model tool.
- **S9 — Members and their subagents modal.** User (L59): "cambio la idea, abrir un modal donde se pueda ver que se esta trabajando, como hacemos con /gentle:agents pero de los miembros y sus sub agentes". Replaces the L58 request to open a child with `--resume` in a new window.
  Acceptance: in the fleet controller TUI, a modal like `/gentle:agents` shows the fleet members and each member's subagents and what they are working on.
- **S10 — Review fixes before the tracker reaches main (L64, L65).** User (L64): "si" to the proposal: one correction PR at the tip of the chain fixing the majors still present at the head, plus the flaky CI test, each with a RED test first, verified independently (Risk items 2, 4). Acceptance:
  - **R1** A fleet member never runs autonomous guardrails: `autonomousMode` from `runtime-guardrails.json` (global or project) is ignored for `fleetRole === "member"`; a member's guarded commands (e.g. `git push`) ask (relayed to the fleet/human). Non-member sessions keep reading the file exactly as before.
  - **R2** A dialog that opens while a deck overlay (alt+w members modal or zoom) is open is never answered or navigated by keys the human cannot see: the deck's overlays close or hide when they lose focus to a dialog; Enter/arrows/digits typed then reach nothing hidden.
  - **R3** The focal item is pinned when focal mode is entered; if the focal item changed (another id) when a digit is pressed, focal mode ends and the key is consumed without answering anything.
  - **R4** Adoption: the hand-off file is the source of truth: `accepted` or `ready` with the same pid counts as accepted regardless of ack timing; when the fleet gives up (turn/exit timeout, controller shutdown or new session), it marks the hand-off `abandoned` and the target re-reads it before `ctx.shutdown()` and stays open (with a notice) when abandoned.
  - **R5** Resume never runs two processes for one member: a live owner (pid lock per fleet session, checked with `process.kill(pid, 0)`) or a live member pid blocks resuming that member with a Blocker.
  - **R6** Fleet git calls never block the controller without a bound: `runGit` has a timeout and a timeout is a typed refusal with nothing left half-created that the fleet does not report.
  - **R7** The test "the controller's live mode is read through the real yolo host channel" is deterministic (waits for the condition, not a fixed number of ticks).
