# Installer: update an older Pi instead of blocking
Objective: the browser installation wizard updates an existing Pi older than the required minimum, shown in the plan before consent, with the package manager that installed it.
Branch: fix/installer-update-older-pi (from origin/main c0672bb08). Delivery: single PR, merge with green CI, then regenerate the v4.0.0 double-click installers. Test runner: `node --experimental-strip-types --test tests/<file>.test.ts`.

## Specs
- S1. User (verbatim): "si pero si no la tiene dijimos que lo instalabamos nosotros y si la tiene y esta vieja deberiamos de actualizarlo no?" — an existing Pi older than the minimum is updated by the installer instead of blocking with `incompatible-tool`. Absent Pi keeps being installed as today.
- S2. User (verbatim): "indicando antes al usuario obvio" — the update appears in the plan the user reviews before the consent checkbox/button, with the current and target version and the package manager; nothing runs before consent.
- S3. The update uses the package manager that owns the existing Pi (pnpm global or npm global), mirroring the Gentle Shell update. Never downgrade; target is the version the installer installs (PI_INSTALL_VERSION, 1.0.0). A Pi the installer cannot attribute to pnpm or npm (mise, Homebrew, binary, link, Windows npm without attribution) no longer blocks: the installer installs its pinned Pi alongside exactly as when Pi is absent (pnpm global, PI_INSTALL_VERSION), without touching the other installation; the plan says so before consent and states that Gentle Shell uses the installer's Pi. (Revised by L6; previously: keep blocking.)
- S4. No regression: reusable Pi, absent Pi, Gentle Shell install/update paths, Windows paths and the CI installer suites keep their behavior; after an update the next run must see a single, reusable Pi (no duplicate/ambiguous pnpm global entries).
- S5. Docs and wizard copy match the new behavior (README "An existing Pi is reused, never reinstalled or downgraded", docs/install-wizard.md existing-installations table and blockers).
- S6. User (verbatim): "tenemos que hacer lo mismo con go o cualquier dependencia" and chose "Copia fijada al lado (recomendado)": an existing Node, pnpm or Go older than (or, for pnpm, incompatible with) the requirement no longer blocks; the installer acquires its pinned, verified version the same way it does when the tool is absent, without modifying or removing the user's installation. The plan states this before consent; for Node and pnpm it states that the installer uses its pinned copy and persists it, without promising PATH precedence (version managers such as `mise activate` re-prepend their own paths on every prompt); Go is used only for the build. (Revised by L6.)
- S7. User (verbatim): "una cosa, no se puede usar lo que tenga el user? mas generico? porque por ahi tambien usa volta, u otros, no se puede hacer which npm y usar la del user y listo?" and chose "Sí, sumalo": on POSIX the first `npm` on the user's PATH is accepted when it works in the user's environment (`npm --version` prints a stable version, `npm config get prefix` prints an absolute path), whatever installed it (mise, Volta, asdf, nvm, fnm, Homebrew, Node's bundled npm). The installer persists its own npm only when no working npm resolves, so a working user npm never triggers `persist-npm`. Windows keeps today's rule in this change.
- Assumption (parent): only an OLDER Pi is updated; a Pi that reports a usable version is never touched; an unusable/unknown Pi keeps today's behavior.
