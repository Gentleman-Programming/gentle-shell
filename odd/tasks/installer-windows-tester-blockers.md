# Installer: Windows tester blockers (private storage, hidden errors, MSYS tar)
Objective: make the browser installer work on the Windows profile the beta tester reported, and show the real cause when a step fails.
Branches: fix/installer-windows-surface-errors (PR A: T1, T2) and fix/installer-windows-private-storage (PR B: T3), both from origin/main 2d7ab4ba3. Delivery: two PRs, each merged with green CI after independent verification, then the v4.0.0 installers are regenerated. Test runner: `node --experimental-strip-types --test tests/<file>.test.ts`; Windows-native tests run only in the `installer (windows-latest)` CI lane.

## Specs
- S1. Tester report, blocker 1 (verbatim): "Bootstrap: private storage ACL/reparse/ownership claim failed or policy denied it. Reason: acl-mask", then "Reason: home-owner" with USERPROFILE; "AppData y LocalAppData tenían permisos adicionales de modificación para otros principales. El propietario del perfil era SYSTEM."; "La carpeta nueva pertenecía a Administradores, así que también fallaba la validación de propietario." User chose "Plan recomendado": (a) when %LOCALAPPDATA% fails with `acl-mask` or `home-owner`, try exactly one alternative, a new folder under %USERPROFILE%, with every ancestor check intact; (b) the base folder's owner may be the user, SYSTEM or BUILTIN\Administrators; (c) the created private folder is explicitly owned by the current user; (d) when nothing passes, the error names the folder and the principal with write access. Unchanged: a %LOCALAPPDATA% or AppData writable by another principal is never used to run binaries. The Node-side storage check (scripts/installer-windows.mjs verifyWindowsStorage) must accept the same tools location.
- S2. Tester pending item (verbatim): "Mostrar en el instalador la causa interna del fallo de Go, no solo install-shell-main." The postinstall (scripts/install-gentle-ai.mjs) prints the whole `error.cause` chain, including a bounded tail of the failing command's stderr; the runner passes a bounded, sanitized detail (home as ~) for `install-global`, `install-shell-main`, `build-gentle-ai-main` and `update-shell` failures; server and wizard show it like the existing setup detail; GitHub's anonymous API rate limit gets the existing rate-limit guidance.
- S3. Root cause (run 38063142924): the Windows source build ran Go inside the installed package; from the pnpm 11 store path of a main package (179 chars) Go's `asm.exe` fails with `The directory name is invalid` because the build's working directories exceed MAX_PATH. The build runs in a short private mkdtemp directory under the system temp directory; the verified binary is published into the package as before.
- S4. Confirmed defect (run 38061123855): with Git for Windows' usr\bin before System32 on PATH, `tar -xzf D:\...` fails with "tar (child): Cannot connect to D: resolve failed". On win32 the main channel (packMainShell, used by install-shell-main and `gentle-shell upgrade --channel main`) runs %SystemRoot%\System32\tar.exe by absolute path, never a `tar` from PATH; a native Windows test puts Git's usr\bin first on PATH.
- S5. Tester pending item (verbatim): "Automatizar la preparación segura de la carpeta temporal y el PATH necesario." Temporary folder: S1. PATH: the runner already puts $PNPM_HOME\bin first in its children (scripts/installer-runner.mjs:220-225); the tester's "is not in PATH" error came from a manual shell. No runner change unless reproduced; the final screen already tells the user to open a new terminal.
