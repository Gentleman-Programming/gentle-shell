# tower-lan-mobile — Gentle Tower: opt-in LAN URL with QR, and a mobile layout
Objective: open Gentle Tower from a phone on the same network through a generated URL, and make the tower web view usable on that phone.
Branch: `feat/tower-lan-mobile` from `main` @ `0d181e872` · Delivery: `ask-on-risk` · Tests: focused `node --experimental-strip-types --test tests/<file>.test.ts`; full `node scripts/run-test-suite.mjs`; types `node scripts/check-types.mjs`; runtime modules `node scripts/build-runtime-modules.mjs --write` then `--check`; web `cd web/tower && npx -y pnpm@11.1.1 install --frozen-lockfile && npx -y pnpm@11.1.1 run build`.

## Specs
User strings are quoted verbatim (Spanish, as written). Evidence baseline: `lib/tower-server.ts:35,168-178,215-222`, `lib/gentle-shell-launcher.ts:181-216,1383,1432`, `README.md:221-231`, `docs/gentle-shell.md:533-569`, `web/tower/src/*` (Pixi scene plus DOM panels; `style.css` has no responsive rules).

S1 — Opt-in LAN URL. `gentle-shell tower --lan` binds the server on all IPv4 interfaces (`0.0.0.0`) instead of `127.0.0.1`, and the text output prints one URL `http://<ip>:<port>/<token>/` for each non-internal IPv4 address of the machine (excluding link-local `169.254.0.0/16`), after the loopback URL. The first LAN address (private ranges first) is the primary URL. The `--json` output keeps every existing field with the same names and values and adds `lan: boolean` and `urls: string[]` (loopback first). Request: "lo ideal seria es que si estoy en la misma red pudiese verlo desde el telefono yendo a una url generada". Checks: launcher test with `--lan --json` (every non-internal IPv4 address from `os.networkInterfaces()` appears in `urls`; with no such address, `urls` holds only the loopback entry); a request over the LAN address with the token is served.

S2 — QR in the terminal. In `--lan` mode the text output includes an ASCII QR code of the primary LAN URL (none in `--json` mode, which stays one line). The encoder is vendored under `lib/` with no new runtime dependency, keeping its MIT license notice. The terminal rendering uses a four-module quiet zone, the QR Code Model 2 spec's margin (review finding; was two). Decision: "Opt-in --lan, token en URL + QR (recomendado)". Checks: `tests/tower-qr.test.ts` pins the module matrix for three URLs (loopback, LAN IP, and a URL with a 63-character path) against fixtures in `tests/fixtures/tower-qr/`; the fixture matrices were decoded back to their URLs by an independent decoder (`jsqr`) in a scratch script outside the repository, recorded in the Log; a launcher test asserts the QR block appears in text output and not in JSON output.

S3 — Token unchanged in LAN mode. The per-launch token is still the first path segment, still required on every HTTP request and on the WebSocket upgrade, and still compared in constant time through the existing `sameToken`. Checks: without token and with a wrong token the request is denied (same denial as today); with the right token through the LAN address it is served.

S4 — Origin and Host in LAN mode. Every request's `<Host header>` must be in the allowlist built at launch — `127.0.0.1`, `localhost` and each enumerated LAN address, with canonical HTTP authorities so port 80 approves both the bare host and the explicit `:80` — even an Origin-less navigation GET (review finding: the Host rule now applies before the optional Origin comparison). A request carrying `Origin` is additionally accepted only when `Origin === "http://" + <Host header>`. `POST` without `Origin` is denied. Every other case gets the existing `deny` response. Checks: accepted (LAN IP host with the same origin); denied (foreign origin `http://evil.example`); denied (Host `evil.example:<port>` with a matching Origin, the DNS-rebinding case); denied (Host `evil.example:<port>` with a valid token and no Origin); denied (loopback Origin with a LAN Host); denied (`POST` without `Origin`); `lanAllowedHosts` pinned for port 80 and a non-default port.

S5 — Default unchanged. Without `--lan` the server binds `127.0.0.1` only, keeps the current origin rule (`Origin` must be exactly `http://127.0.0.1:<port>`; `localhost` is not added to the default allowlist) and the current token rule. Checks: `tests/tower-actions.test.ts` and the existing tower tests pass unmodified; in default mode `urls` is `[<loopback url>]` and `lan` is `false`.

S6 — In-session command. `/gentle:tower --lan` starts the same LAN mode from a session and surfaces the LAN URLs and the warning where `/gentle:tower` surfaces the loopback URL today; `/gentle:tower` without the flag is unchanged. `/gentle:tower-mobile` is the one-word form of the same-network mode (user request, review finding: the server is reused while the mode matches and replaced, closing the running one, when it changes). Checks: `tests/gentle-tower.test.ts` covers both forms, the mobile command, both mode-change orders and same-mode reuse.

S7 — Warning. In `--lan` mode the text output and the in-session report print a warning stating that anyone on the network who opens the URL can read and drive the sessions, that the traffic is not encrypted, and that it is meant for a trusted home network. Request: "gestionar pi y las sesiones desde el telefono mientras estoy en la casa (osea la misma red". Checks: the warning line is present in `--lan` text output (launcher test) and in the extension's report (extension test); JSON output may carry the same text in a `warning` field and still prints one line.

S8 — Help and docs. Update the launcher help (`lib/gentle-shell-launcher.ts`, the `tower` usage and description lines), `README.md` (tower section, today "it listens on `127.0.0.1` only"), `docs/gentle-shell.md` (tower section) and any other doc line stating the loopback-only model for the tower, to describe `--lan`, the QR, the warning, the trust model (home network, HTTP without encryption), and that `--port` with `--lan` binds every interface. Checks: `grep -n '127.0.0.1` only' README.md docs/*.md` returns no tower statement contradicting the new behavior; any test pinning the help text is updated.

S9 — Mobile layout. At a viewport width of 720 CSS px or less, or with a coarse pointer, the tower web app lays out for a phone: the Pixi building fits the viewport width with a minimum floor height of 44 CSS px (the scene scrolls vertically when the floors do not fit), and the panels — Talk, Todo, Artifacts, Library/usage and the floor controls — become tabs in a bottom sheet; Talk gets a visible button, not only the `T` key. Decision: "Responsive con hoja inferior (recomendado)"; request: "que esta vista de tower tuviese una vista mobile". Checks: `tests/tower-responsive.test.ts` covers the pure layout functions (`fitBuilding`, the sheet decision) at 390x844, 768x1024, 1440x900 and with many floors; `tsc --noEmit && vite build` pass; the built CSS contains the narrow-width media query.

S10 — Touch and viewport. Floors and sheet tabs are at least 44x44 CSS px tap targets; the scene hit-testing uses pointer events; `touch-action: manipulation`; the app height uses `100dvh` and honours `env(safe-area-inset-*)`. Checks: `tsc --noEmit && vite build`; a structural probe of the built `dist` (media query, `100dvh`, `touch-action` present).

S11 — Reconnection (assumption: a phone loses Wi-Fi more often than a desktop; if the client already reconnects and refetches the snapshot, this task only records the proof). When the WebSocket drops, the client reconnects with capped exponential backoff and fetches a fresh snapshot, so the view resumes without a manual reload. Checks: a test of the backoff schedule if a new one is written; otherwise the evidence recorded in the Log.

S12 — Desktop unchanged. At desktop widths with a fine pointer the layout and interactions stay as today: no bottom sheet, keyboard `T` still opens Talk. Checks: the existing tower tests pass; the structural probe shows the desktop rules untouched (additive CSS only).
