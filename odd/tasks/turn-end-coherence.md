# Turn-end coherence: one rule for ending a turn, consistent across prompt, tools and notices
Branch `feat/turn-end-coherence`, worktree `.worktrees/turn-end-coherence`, baseline `8c4f86f57` (origin/main). Local work-unit commits only; no push, PR or merge without the user.
Runner: `node --experimental-strip-types --test <file>`; `pnpm run typecheck`; suite `pnpm test`. Diagnosis that motivates this work: Engram `diagnostics/premature-settlement-gpt-family`.

## Specs

S1. One end-of-turn rule, stated positively and before any prohibition. Approved plan, step 2: "Escribir una sola regla de fin de turno, en positivo y al principio. Un turno termina solo si el resultado pedido está entregado y verificado, si espera trabajo ya lanzado, si falta una decisión o consentimiento tuyo, o si se agotó un límite explícito. Todo lo demás es un obstáculo: diagnosticar, cambiar de enfoque y seguir."
Examples the rule must decide the same way every time:
- A command, test or tool fails, times out or returns nothing, and another permitted approach exists: the turn continues (obstacle).
- A sub-step finished and the requested deliverable still needs a step the agent can run now (for example the asset is placed and the export was never launched): the turn continues and runs it.
- A background job or subagent the agent launched is still running and nothing independent remains: the turn ends (wait) and resumes on the completion event.
- A decision, consent or permission only the human can give is missing, or the human said stop: the turn ends for the work that applies to.
- An explicit one-run, no-retry or diagnostic-only limit, or an exhausted correction budget, covers the failed action: that action is not repeated; independent work continues.

S2. Approved plan, step 3: "Fijar tres términos y usarlos igual en todos lados. *Obstáculo* (fallo ordinario, se sigue), *límite* (explícito, vale solo para lo que nombra) y *espera* (trabajo lanzado, se retoma solo)." In English artifacts: obstacle, limit, wait. Text touched by this work never uses "stop", "blocked" or "denial" for an ordinary failure.

S3. Approved plan, step 4: "Acotar cada prohibición a su caso. No existing protection is weakened: explicit human limits, provider consent, exact-token authorization, publishing and destructive-action permission, native review authority, worker prohibitions and the bounded recovery of #2919 keep their meaning.

S4. Approved plan, step 5: "Alinear herramientas y avisos con la regla. Reescribir la frase de timeout de `bash_background`, el resultado de lanzar un job y el aviso de fin de job para que digan lo mismo que el prompt." Current strings: "Report a timeout as failure; never automatically retry, restart, or migrate it to background." and "You will be notified once when it exits; keep working or end your turn." A timeout stays a reported failure and is never re-run unchanged; the text must say what to do next (read the output, fix the cause, then run again). The launch result and the job-exit notice must state continuation the way the subagent wake does ("Review it and continue.").

S5. Approved plan, step 7: "Dar paridad a GPT. Incluir en el prompt propio el equivalente de «Finishing work»." Reference text only Claude receives today, from its bridge: "Ending your turn means your work stops there until asked to continue, and you should not stop unless needed. Please avoid stopping while work the user asked for is still owed. [...] You may meet ordinary obstacles like errors, timeouts, locked files, empty results or failing tools. Diagnose them first, and when they are not real blockers, work through them with the access you have (wait and retry, fix the request, use another tool or source) rather than stopping or checking in. If someone clearly decided something is a hard blocker, such as a file marked not to be touched, access that was intentionally withheld, or a safety guardrail, leave it alone, say plainly what you found, and look for another way to finish the task." S11. Replace the attempt counter with a progress rule. User: "hay una que odio que quieor sacar, la de \"numero de intentos\" eso porque estaba?"; decision: "Cambiar el contador por una regla de progreso (recomendado)". Today `assets/agents/gentle-ai-worker.md` says: "Make one correction attempt per failing check, and a second only if the same check still fails after a real fix; then stop and return `status: partial` with the failing command and its output, never looping." New rule, for every writer agent that carries a counted correction bound and for the parent's recovery paragraph: a worker keeps correcting a failing check while each attempt names a cause from the output and changes something for that reason; it stops and returns `status: partial` only when the same cause fails again after a real fix and no new hypothesis exists, when passing would require weakening, skipping or rewriting the check, or when the fix needs work outside its allowed surfaces or crosses an explicit limit. It never repeats the same change and never stops because a number of attempts was reached. What stays: the content of the partial handoff (failing commands and outputs, remaining work, missing proof, diagnosed cause with evidence), "That ends your cycle, not the unit", no fresh cycle and no reset in a new session once stopped for a repeated cause, RED construction kept separate from fix correction, the parent's recovery routes of #2919 in both delegation modes, native review correction budgets and explicit one-run, no-retry and diagnostic-only limits. Byte rule of S6 applies.
